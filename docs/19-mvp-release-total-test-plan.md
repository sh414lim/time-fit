# TimeFit MVP 배포 전 전체 테스트 시나리오

## 1. 목적

출시 전 TimeFit의 관리자 웹, 직원 웹, 태블릿 출퇴근·휴가 신청이 역할·사업장·개인정보 경계를 지키며 동작하는지 검증한다. 이 문서는 기능 통과만이 아니라 **다른 직원·다른 사업장·비로그인 사용자에게 정보가 노출되지 않는지**를 출시 판정 기준으로 포함한다.

## 2. 환경과 역할

| 역할 | 계정/상태 | 검증 범위 |
| --- | --- | --- |
| 관리자 A | 사업장 A 소유자 | 직원·근태·휴가·운영 설정 관리 |
| 직원 A-1 | 사업장 A 소속 | 자기 일정·근태·휴가만 확인 |
| 직원 A-2 | 사업장 A 소속 | 동일 사업장 내 다른 직원 |
| 관리자 B | 사업장 B 소유자 | 사업장 A와 분리된 데이터 |
| 비로그인 사용자 | 로그인 없음 | 로그인 화면, 태블릿 공개 입력 화면만 접근 |

테스트 시 사용되는 전화번호·이메일·휴가·근태는 모두 테스트 데이터여야 한다. 실제 직원 개인정보를 사용하지 않는다.

## 3. 출시 판정 기준

### 출시 차단(Blocking)

- 직원이 다른 직원의 전화번호, 휴가 사유, 급여, 상세 근태를 볼 수 있음
- 관리자 B가 사업장 A의 직원·근태·휴가·설정에 접근 가능
- 비로그인 사용자가 관리자 웹 데이터에 접근 가능
- 태블릿에서 잘못된 PIN/전화번호로 출퇴근·휴가 신청이 저장됨
- 휴가 승인·반려나 출퇴근 기록이 다른 사업장에 반영됨
- 비밀정보(API 키, DB URL, 서비스 키)가 브라우저 화면·콘솔·빌드 결과에 노출됨

### 출시 허용 조건

- 모든 Blocking 항목이 PASS
- 핵심 흐름(로그인 → 설정 → 출근/퇴근 → 휴가 신청 → 관리자 확인)이 PASS
- 알림은 카카오 연동 전에는 `queued`/`disabled` 기록과 안내 문구가 일치
- 알려진 제한 사항이 운영자 문서에 기록됨

## 4. 인증·세션·권한 테스트

### AUTH-01. 비로그인 접근 차단

1. 로그아웃 상태에서 루트 URL을 연다.
2. 관리자 URL/직원 관리 메뉴가 보이는지 확인한다.
3. 브라우저 주소로 관리자 화면 경로를 직접 입력한다.

기대 결과: 로그인 화면으로 유도되며 사업장·직원·근태 데이터가 노출되지 않는다.

### AUTH-02. 관리자와 직원 메뉴 분리

1. 관리자 A로 로그인한다.
2. 관리자 전용 메뉴(직원 관리, 운영 설정, 급여 관리)를 확인한다.
3. 직원 A-1로 로그인한다.
4. 동일 메뉴가 숨겨지거나 접근 거부되는지 확인한다.

기대 결과: 직원은 관리자 운영 기능과 타 직원 상세에 접근할 수 없다.

### AUTH-03. 로그아웃 후 화면 잔존 데이터

1. 관리자 A로 직원 상세를 연다.
2. 로그아웃한다.
3. 뒤로 가기, 새로고침, 최근 탭 복구를 수행한다.

기대 결과: 이전 화면의 직원 이름·전화번호·휴가·근태가 다시 표시되지 않는다.

### AUTH-04. 역할 변경 및 초대 수락 경계

1. 사업장 연결 전 직원 계정으로 로그인한다.
2. 관리자 기능 접근을 시도한다.
3. 초대 수락 후 새로고침한다.

기대 결과: 초대 전에는 개인 고유번호 외 사업장 데이터가 없고, 수락 후에도 직원 권한만 부여된다.

## 5. 사업장 간 데이터 격리 테스트

### ISOLATION-01. 관리자 간 격리

1. 관리자 A에서 직원 A-1의 근태·휴가·전화번호를 생성한다.
2. 관리자 B로 로그인한다.
3. 직원 관리, 휴가·연차, 출퇴근, 운영 설정을 각각 확인한다.

기대 결과: 사업장 A의 이름, 직원, 신청, 전화번호 뒷자리, 근태가 관리자 B에게 전혀 보이지 않는다.

### ISOLATION-02. 태블릿 사업장 URL 격리

1. 사업장 A의 태블릿 URL을 연다.
2. 직원 B의 전화번호 뒷 4자리/8자리와 사업장 A의 PIN을 입력한다.
3. 사업장 B의 태블릿 URL에서도 반대로 수행한다.

기대 결과: 다른 사업장 직원은 확인되지 않으며 출퇴근·휴가 기록이 생성되지 않는다.

### ISOLATION-03. URL 파라미터 변조

1. 태블릿 URL의 `organization` 값을 다른 사업장 ID로 바꾼다.
2. 기존 사업장 PIN·직원 번호로 인증한다.

기대 결과: 사업장별 설정과 직원 번호가 동시에 일치할 때만 처리된다.

## 6. 관리자 정보 노출·개인정보 테스트

### PRIVACY-01. 직원 전화번호 표시 최소화

1. 관리자 직원 목록과 직원 상세를 확인한다.
2. 직원 A-1로 로그인해 자기 화면을 확인한다.
3. 직원 A-2 정보로 이동할 수 있는 모든 목록·링크를 확인한다.

기대 결과:

- 전체 전화번호는 관리자 전화번호 등록/수정 플로우에서만 사용한다.
- 직원은 다른 직원의 전체 번호·뒷자리·개인 상세를 볼 수 없다.
- 일반 목록에는 전화번호 대신 이름·부서·직책 등 최소 정보만 표시한다.

### PRIVACY-02. 휴가 정보 최소 노출

1. 관리자 A에서 휴가 목록·상세를 확인한다.
2. 직원 A-1에서 본인 휴가 내역을 확인한다.
3. 직원 A-2에서 A-1의 휴가 사유·날짜·승인 메모가 보이는지 확인한다.

기대 결과: 관리자에게는 검토에 필요한 정보만, 직원에게는 본인 요청 결과만 보인다.

### PRIVACY-03. 급여 정보 접근 제한

1. 관리자 A와 직원 A-1 각각으로 로그인한다.
2. 급여 관리 메뉴와 URL 직접 접근을 시도한다.
3. 직원 상세에 시급·월급·예상 급여가 어떤 역할에 표시되는지 확인한다.

기대 결과: 급여 원천 정보와 계산 결과는 관리자에게만 노출된다. 직원에게는 본인 급여 기능이 출시 전 미구현이면 메뉴와 데이터가 노출되지 않는다.

### PRIVACY-04. 관리자 연락처·운영 정보

1. 직원 계정에서 운영 설정과 관리자 상세 접근을 시도한다.
2. 태블릿 화면에서 사업장 주소·관리자 연락처가 보이는지 확인한다.

기대 결과: 태블릿에는 인증에 필요한 최소 안내만 노출하고, 주소·관리자 전화번호·운영 설정은 관리자 전용이다.

### PRIVACY-05. 브라우저 및 네트워크 노출 점검

1. 로그인/직원 관리/태블릿 페이지의 브라우저 콘솔 오류를 확인한다.
2. 배포된 JavaScript 파일과 화면에 서비스 역할 키, DB 접속 문자열, 관리자 전체 전화번호가 포함되는지 점검한다.
3. 오류 메시지에 SQL·내부 테이블·민감한 입력값이 표시되는지 확인한다.

기대 결과: 공개 클라이언트에는 publishable/anon 키만 존재하며, 서비스 역할 키와 DB URL은 노출되지 않는다.

## 7. 핵심 운영 플로우 테스트

### FLOW-01. 관리자 준비 → 직원 출근

1. 관리자 A가 운영 설정(PIN 활성화)과 직원 A-1 전화번호를 등록한다.
2. 태블릿에서 A-1의 PIN·전화번호 뒷 4자리로 직원 확인을 한다.
3. 출근을 저장한다.
4. 관리자 출퇴근 화면과 직원 상세에서 기록을 확인한다.

기대 결과: 당일 출근 1건이 사업장 A, 직원 A-1로 저장된다.

### FLOW-02. 출근 → 퇴근 중복 방지

1. FLOW-01 직후 다시 직원 확인한다.
2. `퇴근하기`가 표시되는지 확인하고 저장한다.
3. 다시 퇴근을 시도한다.

기대 결과: 출근 1회·퇴근 1회만 저장되고 중복 처리는 차단된다.

### FLOW-03. 직원 휴가 신청 → 관리자 알림 대기열

1. 관리자 A의 수신 전화번호를 등록한다.
2. 태블릿에서 A-1의 PIN·전화번호 뒷 8자리로 미래 날짜 연차를 신청한다.
3. 휴가 신청 성공과 `관리자 알림 발송 대기열` 문구를 확인한다.
4. 관리자 휴가 목록과 알림 로그를 확인한다.

기대 결과: 휴가 요청은 `pending`, 출처는 `tablet`, 알림 로그는 `queued`이다.

### FLOW-04. 관리자 승인·반려

1. 관리자 A가 FLOW-03 요청을 연다.
2. 승인 메모를 입력하고 승인한다.
3. 별도 요청을 만들고 반려 사유를 입력해 반려한다.
4. 직원 A-1이 자신의 결과를 확인한다.

기대 결과: 승인/반려 상태와 검토 정보가 영속화되고 대상 직원에게만 반영된다.

## 8. 입력 검증·악용 방지 테스트

| ID | 시도 | 기대 결과 |
| --- | --- | --- |
| VALID-01 | PIN에 문자·5자리 입력 | 숫자 4자리만 허용 |
| VALID-02 | 전화번호에 문자·길이 오류 | 4/8자리 숫자만 허용 |
| VALID-03 | 과거 날짜 휴가 신청 | 차단 |
| VALID-04 | 태블릿 비활성 후 신청 | 차단 |
| VALID-05 | 다른 사업장 번호 사용 | 직원 확인 실패 |
| VALID-06 | 빠른 반복 제출 | 중복 기록/중복 요청이 비정상 생성되지 않음 |
| VALID-07 | 승인 권한 없는 직원이 승인 API 호출 | 권한 거부 |

## 9. 카카오 알림톡 출시 전 확인

현재 MVP는 휴가 신청 시 알림 로그를 생성한다. 실제 카카오 발송은 다음이 준비된 뒤 별도 통합 테스트를 수행한다.

1. 카카오 비즈메시지 공급사 계정, 발신 프로필, 승인 템플릿을 등록한다.
2. 서버에 공급사 비밀 키를 환경변수로만 등록한다.
3. `queued` 로그를 발송하는 서버 작업을 구성한다.
4. 성공 시 `sent`, 공급사 오류 시 `failed`로 상태가 변하는지 확인한다.
5. 같은 휴가 요청이 중복 발송되지 않는지 확인한다.
6. 실제 수신 번호에 템플릿 메시지가 1회 수신되는지 확인한다.
