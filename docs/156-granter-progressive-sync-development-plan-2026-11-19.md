# Granter 점진 동기화 개발 기획

## 목표

- 지출·증빙 진입 후 30초 안에 현재 월의 사용 가능한 데이터를 표시한다.
- 일부 원천이 429 또는 일시 장애여도 성공한 원천의 거래와 그래프는 사용할 수 있어야 한다.
- 전체 기간 조회는 브라우저 요청 시간과 분리하고, 페이지 재진입 시 기존 스냅샷을 즉시 표시한다.

## 사용자 흐름

1. 사용자가 `지출·증빙 > 재무 통합`에 진입한다.
2. 최근 정상 스냅샷이 있으면 즉시 표시하고 마지막 동기화 시각을 안내한다.
3. 스냅샷이 없으면 현재 월 원천을 제한된 재시도 정책으로 순차 조회한다.
4. 성공 원천은 즉시 집계하고 실패 원천은 `재시도 가능` 상태로 분리한다.
5. 사용자가 `전체 기간`을 선택하면 백그라운드 동기화를 시작하고 원천별 진행률을 표시한다.
6. 화면을 이동해도 동기화는 계속되고, 다시 돌아오면 기존 진행률과 결과를 복원한다.

## UI/UX

- 상단 연결 상태: 워크스페이스, API 리비전, 마지막 성공 시각을 표시한다.
- 진행 상태: `8/12개 원천 완료`처럼 완료·실패·대기 원천을 구분한다.
- 부분 완료: 성공 데이터는 그래프와 목록에 즉시 표시하고 경고 배너에서 실패 원천을 안내한다.
- 재시도: 전체 재수집이 아닌 실패 원천만 다시 요청한다.
- 전체 기간: 버튼을 누르면 진행률 패널을 열고 완료 후 자동으로 전체 기간 스냅샷을 전환한다.

## 백엔드 구조

### 1단계: 제한시간 내 부분 응답

- 현재 월은 외부 API 재시도를 요청당 1회로 제한한다.
- 429·5xx가 발생한 원천은 실패 상태로 반환하고 성공 원천 집계를 유지한다.
- 일시 실패가 포함된 응답은 서버 메모리 캐시에 저장하지 않는다.
- 인증 실패(401·403)는 즉시 중단하고 명확한 연결 오류로 처리한다.

### 2단계: 영속 스냅샷

- `timefit_user_granter_sync_runs`: 동기화 실행, 범위, 상태, 진행률, 오류를 저장한다.
- `timefit_user_granter_source_snapshots`: 조직·범위·원천별 정규화 결과와 체크포인트를 저장한다.
- 서비스 역할만 쓰기 가능하게 하고, 사용자 조회는 기존 재무 권한 API를 통한다.
- 완료된 원천 스냅샷을 합쳐 화면용 집계를 반환한다.

### 3단계: 백그라운드 전체 기간 동기화

- Vercel Workflow에서 원천별·기간 창별 단계를 실행한다.
- 단계마다 체크포인트를 저장해 실패 후 이어서 실행한다.
- 429는 서버가 제공하는 재시도 시각을 우선하며 지수 백오프를 적용한다.
- 프런트는 실행 ID를 받아 진행률만 조회하고 장시간 HTTP 연결을 유지하지 않는다.

## API 계약

- `GET /api/granter-finance-analytics?scope=period`: 최근 정상 스냅샷 또는 제한시간 내 부분 결과.
- `POST /api/granter-finance-sync`: 전체 기간 또는 실패 원천 동기화 시작.
- `GET /api/granter-finance-sync?id=...`: 원천별 진행률과 오류 상태.
- `GET /api/granter-finance-analytics?scope=all`: 완성된 전체 기간 스냅샷 조회.

## 완료 기준

- 현재 월 최초 조회가 120초 클라이언트 제한을 초과하지 않는다.
- 한 원천의 429가 다른 원천 데이터 표시를 막지 않는다.
- 부분 응답 재조회 시 실패 원천이 다시 시도된다.
- 페이지 이동 후에도 마지막 스냅샷과 선택 범위가 유지된다.
- 운영 로그에서 인증 실패, 요청 제한, 원천별 처리 시간을 구분할 수 있다.
