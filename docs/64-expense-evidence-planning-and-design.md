# TimeFit 지출 증빙·매출 연동·자동결산 최종 기획 및 설계안

작성일: 2026-09-10  
대상: 관리자 웹의 기존 `세금 · 전표` 영역 확장
문서 상태: 최종 기획안 v1.0

## 0. 확정 범위

이 문서는 다음 기능의 제품·화면·데이터·서버 설계 기준이다.

- 휴대폰으로 영수증 촬영 및 사진/PDF 업로드
- Google Cloud Vision을 통한 이미지 텍스트 변환
- LLM을 통한 지출 필드 JSON 구조화
- 사용자의 원본/추출 결과 확인 및 지출 확정
- 법인카드 승인내역 수집과 영수증 매칭
- 카드내역·영수증·수기 입력의 중복 지출 방지
- 기존 Toss Place 매출과 지출 원장 연동
- 일간·주간·월간·연말 결산 자동 생성
- 관리자 예외 중심 검수, 마감 및 세무 자료 전달

이번 버전에서 가장 중요한 제품 목표는 **관리자가 모든 거래를 입력하는 시스템이 아니라, 시스템이 자동 처리한 결과 중 예외만 확인하는 시스템**을 만드는 것이다.

## 1. 결론

기존 `세금 · 전표` 화면은 파일 보관과 세무사 전달 기능 중심이다. 이를 바로 교체하기보다 상위 메뉴를 `지출 · 증빙`으로 확장하고 다음 4개 하위 탭으로 분리한다.

1. **지출 내역**: 확정·검수된 지출 원장
2. **증빙 검토**: 사진/PDF 업로드, OCR·AI 추출 결과 확인 및 수정
3. **법인카드**: 카드 등록, 승인내역 조회, 증빙 자동 매칭
4. **정산 자료**: 기존 세금계산서·매출전표 보관 및 세무사 전달

핵심 원칙은 `파일`, `AI 추출 결과`, `지출 원장`, `카드 승인내역`을 서로 다른 데이터로 보관하고 연결 관계로 묶는 것이다. AI 결과를 곧바로 확정 원장에 넣지 않고 반드시 검증 규칙과 사용자 확인 단계를 둔다.

최종 목표는 증빙 보관이 아니라 **매출과 지출을 연결한 자동 결산**이다. 동일한 원장을 기준으로 일간·주간·월간·연말 결산을 생성하며, 관리자는 정상 건을 일일이 처리하지 않고 시스템이 판단하지 못한 예외만 확인한다.

## 2. Granter 검토 결과

로그인된 `버터빌라` 워크스페이스에서 읽기 전용으로 다음 화면을 확인했다.

- **계좌/전체 거래내역**: 전체·자동 분류·연결됨·제외됨 상태 탭, 검색, 기간, 필터, 자동화, 테이블 설정
- **세금계산서**: 매출/매입 합계, 발급완료·대기·실패·연결 필요, 거래별 연결금액·계정과목·사유
- **현금영수증**: 매출/매입 구분, 사용처·공급가액·세액·승인번호·태그·사유
- **수기관리**: 내역 추가, 종류·거래처·적요·합계금액·수량·공급가액·세액·계정과목·사유
- **사유작성**: 기간 단위 업무 처리와 테이블 보기 전환
- **결재**: 승인대기·승인완료·승인거절·결재완료·내가 작성, 결재 템플릿, 엑셀 다운로드
- **드라이브**: 폴더/파일 업로드와 사용자별 업로드·삭제 활동 이력

가져올 패턴은 다음과 같다.

- 원천 데이터와 업무 상태를 분리한다.
- 거래에 증빙, 계정과목, 사유, 태그, 결재를 연결한다.
- 월 단위 탐색을 기본으로 하고 검색·필터·테이블 설정을 제공한다.
- 자동 처리 결과는 `자동 분류`, 사람이 확인한 결과는 `연결됨`, 제외 대상은 `제외됨`으로 명확히 구분한다.
- 파일 작업과 승인 작업의 감사 이력을 남긴다.

TimeFit은 여기에 모바일 사진 업로드, OCR/LLM 처리 상태, 추출 신뢰도, 카드 승인내역 매칭을 제품의 중심 경험으로 추가한다.

## 3. 사용자 흐름

### 3.1 영수증 등록

1. 관리자가 `영수증 촬영` 또는 `사진에서 가져오기`를 누른다.
2. 모바일에서는 카메라를 바로 실행해 영수증을 촬영한다. 데스크톱에서는 JPG/PNG/HEIC/PDF 파일을 선택한다.
3. 촬영 화면에서 영수증이 프레임 안에 들어왔는지 확인하고 다시 촬영하거나 업로드를 확정한다.
4. 원본 이미지는 비공개 Storage에 먼저 저장되고 즉시 `텍스트 변환 중` 카드가 생성된다.
5. 서버가 원본 또는 보정된 이미지를 Google Cloud Vision API의 문서 텍스트 인식 OCR로 전송한다.
6. Google Vision이 영수증 이미지에 포함된 상호명, 날짜, 금액, 사업자번호, 승인번호 등의 전체 텍스트와 위치 정보를 반환한다.
7. OCR 원문과 최소한의 문서 메타데이터를 LLM에 보내 엄격한 JSON 스키마로 구조화한다. LLM이 영수증 이미지를 다시 읽는 구조가 아니라, 기본적으로 Google Vision이 만든 텍스트를 해석하는 구조로 한다.
8. 금액·부가세·날짜·사업자번호 검증을 실행한다.
9. 신뢰도가 높으면 `검토 가능`, 낮거나 계산이 맞지 않으면 `확인 필요`로 분류한다.
10. 사용자는 원본 영수증 사진과 Vision OCR 원문, 추출 필드를 나란히 확인하고 수정 후 `지출로 확정`한다.
11. 대응 카드 승인내역이 있으면 후보를 보여주고 사용자가 연결하거나 자동 연결한다.

### 3.2 영수증 촬영 UX

- 모바일 웹의 파일 입력은 `accept="image/*"`와 카메라 촬영 옵션을 제공한다.
- 촬영 전 안내선으로 영수증 전체가 화면 안에 들어오도록 유도한다.
- 업로드 전 미리보기에서 `다시 촬영`과 `이 사진 사용`을 분리한다.
- 흐림, 강한 반사, 너무 어두운 사진, 영수증 잘림을 감지하면 OCR 전에 재촬영을 권고한다.
- 긴 영수증은 여러 장 촬영할 수 있고 한 건의 증빙으로 묶는다.
- 여러 영수증이 한 사진에 포함된 경우 자동 확정하지 않고 `확인 필요`로 보낸다.
- HEIC 이미지는 Vision 지원 형식으로 서버에서 변환한 뒤 처리하며 원본도 함께 보관한다.
- 사용자가 화면을 닫아도 서버 처리는 계속되며 목록에서 `업로드 중 → 텍스트 변환 중 → AI 분석 중 → 검토 가능` 상태를 확인할 수 있다.

### 3.3 법인카드 내역

1. 관리자만 카드 연결을 시작한다.
2. 카드사 또는 제휴 데이터 사업자의 인증 화면을 거친다.
3. TimeFit에는 카드 토큰, 카드사, 별칭, 끝 4자리만 저장한다. 전체 카드번호와 CVC는 저장하지 않는다.
4. 승인내역을 주기적으로 동기화하고 신규 내역을 `미증빙`으로 표시한다.
5. 금액·승인일시·가맹점·카드를 기준으로 증빙 후보를 매칭한다.
6. 사용자가 매칭을 확정하면 지출 원장에 연결된다.

초기 MVP에서는 실시간 카드사 연동보다 **카드사 CSV/Excel 업로드**를 먼저 제공한다. 카드사별 인증·약관·비용·망 분리 이슈를 검증한 뒤 API 연동을 2단계로 진행하는 것이 안전하다.

## 4. 화면 설계

### 4.1 공통 상단

- 월 선택, 이전/다음 월
- 검색: 거래처, 사용처, 메모, 금액
- 필터: 상태, 결제수단, 카드, 지출자, 계정과목, 증빙 유무
- 요약 카드: 총 지출, 증빙 완료, 미증빙, 확인 필요
- 주요 버튼: `증빙 추가`, `카드 내역 가져오기`

### 4.2 지출 내역 탭

컬럼: 사용일시, 사용처, 지출자, 결제수단/카드, 합계금액, 공급가액, 부가세, 계정과목, 증빙, 상태.

행을 누르면 우측 상세 패널을 열어 원본, 추출 필드, 카드 내역, 수정 이력, 메모, 승인 이력을 한 번에 보여준다. 대량 선택 후 계정과목/담당자/상태 일괄 변경과 CSV 내보내기를 제공한다.

### 4.3 증빙 검토 탭

- 상태 탭: `처리 중`, `확인 필요`, `검토 가능`, `완료`, `실패`
- 좌측: 영수증 이미지/PDF 미리보기, 확대·회전·다음 장
- 우측: 추출된 필드 폼과 필드별 신뢰도
- 하단 주요 행동: `다시 분석`, `임시 저장`, `지출로 확정`, `제외`
- 실패 시 내부 오류문 대신 재시도 가능한 사용자 메시지와 실패 사유를 표시

### 4.4 법인카드 탭

- 카드 관리: 카드 별칭, 카드사, 끝 4자리, 사용자, 연결 상태, 최근 동기화
- 승인내역 상태: `미증빙`, `매칭 후보`, `연결 완료`, `제외`
- 카드 해제와 동기화 실패 복구 경로
- 동일 금액 다건, 승인 취소, 부분 취소, 해외 결제, 할부, 한 영수증-여러 승인 건을 지원

### 4.5 정산 자료 탭

현재 `세금계산서 · 매출전표` 업로드, 열기, 삭제, 월말 정산 요약 발송 기능을 그대로 이동한다. 지출 내역과 혼동되지 않도록 `파일 보관함`임을 명시한다.

## 5. 처리 상태

증빙 상태는 다음 단방향 흐름을 기본으로 한다.

`uploaded → ocr_processing → extracting → needs_review/ready → confirmed`

예외 상태는 `failed`, `excluded`, `duplicate`이며 재처리 시 새 처리 시도 이력을 추가한다. 이미 확정된 지출은 AI 재분석이 원장을 덮어쓰지 않고 새 제안 버전만 생성해야 한다.

카드 매칭 상태는 `unmatched → suggested → matched`이며 `ignored`, `cancelled`를 별도로 둔다.

## 7. 데이터 모델

### `expense_documents`

원본 증빙 파일. `organization_id`, `storage_path`, `mime_type`, `sha256`, `page_count`, `status`, `uploaded_by`, `created_at`.

### `expense_processing_runs`

OCR/LLM 처리 시도. `document_id`, `attempt_no`, `ocr_provider`, `ocr_text`, `model`, `prompt_version`, `schema_version`, `raw_result jsonb`, `status`, `error_code`, `started_at`, `finished_at`.

### `expenses`

확정 지출 원장. `organization_id`, `document_id`, `occurred_at`, `merchant_name`, `business_number`, `total_amount`, `supply_amount`, `vat_amount`, `currency`, `payment_method`, `expense_category_id`, `spender_staff_id`, `memo`, `review_status`, `confirmed_by`, `confirmed_at`.

### `corporate_cards`

`organization_id`, `provider`, `provider_card_token`, `issuer`, `nickname`, `last4`, `holder_staff_id`, `connection_status`, `last_synced_at`. PAN/CVC는 금지한다.

### `card_transactions`

`corporate_card_id`, `provider_transaction_id`, `approved_at`, `merchant_name`, `amount`, `currency`, `approval_number`, `transaction_type`, `raw_payload jsonb`. `(provider, provider_transaction_id)` 또는 동등 키로 중복을 막는다.

### `expense_matches`

`expense_id`, `card_transaction_id`, `match_type`, `score`, `status`, `confirmed_by`, `confirmed_at`. 분할·합산 매칭을 위해 연결 테이블로 둔다.

### `expense_audit_logs`

생성, 추출, 수정, 확정, 매칭, 제외, 삭제, 내보내기의 actor와 before/after를 기록한다.

모든 테이블은 `organization_id` 기준 RLS를 적용하고, 관리자/소유자만 카드 연결과 확정·삭제를 수행하도록 한다. 직원의 본인 증빙 제출을 허용할 경우 제출과 조회 정책을 별도로 분리한다.

## 8. 서버 아키텍처

```text
Web/Mobile upload
  → Supabase private Storage
  → processing_jobs 생성
  → Edge Function/Worker
      → 이미지 회전·해상도·품질 검사 및 필요 시 형식 변환
      → Google Cloud Vision Document Text Detection
      → OCR 전체 텍스트와 위치 정보 저장
      → LLM structured output
      → schema + accounting validation
  → needs_review/ready
  → 사용자 확정
  → expenses 원장
  ↔ card_transactions 자동 매칭
```

- 브라우저에서 Vision/LLM API 키를 호출하지 않는다.
- 브라우저가 Google Vision으로 직접 사진을 보내지 않는다. 비공개 Storage에 업로드한 뒤 권한이 있는 서버 작업만 Vision API를 호출한다.
- 업로드 API는 파일 형식, 크기, 실제 MIME, 이미지 해상도, 해시 중복을 검사한다.
- 긴 OCR 작업은 요청-응답 안에서 기다리지 않고 큐/잡으로 처리한다.
- 각 단계는 멱등 키를 사용해 새로고침·재시도에도 중복 지출이 생기지 않게 한다.
- 공급가액 + 부가세 = 합계금액, 미래 날짜, 비정상 사업자번호 등 결정적 검증은 코드로 처리한다.
- 자동 확정은 초기에 비활성화하고 운영 데이터로 정확도를 측정한 후 조건부 도입한다.

## 9. 자동 매칭 규칙

초기 점수 예시:

- 금액 정확히 일치: +50
- 승인일시 ±1일: +20, ±3일: +10
- 카드 끝 4자리 일치: +20
- 정규화된 가맹점명 유사: 최대 +10
- 승인 취소/매입 취소 불일치: 매칭 금지

90점 이상은 자동 연결 후보, 70~89점은 사용자 확인 후보, 그 미만은 미매칭으로 둔다. 실제 자동 연결은 운영 검증 후 활성화하며 언제든 연결 해제 가능해야 한다.

## 10. 매출·지출 통합 결산

### 10.1 결산의 기준 원장

모든 결산은 다음 확정 원천을 읽어 생성한다.

- **매출 원장**: Toss Place 등 연동 매출, 취소·환불, 결제수단별 매출
- **지출 원장**: 법인카드, 현금, 계좌이체, 수기 지출
- **증빙 상태**: 영수증, 세금계산서, 현금영수증 및 미증빙 여부
- **인건비**: 확정 급여, 사용자 부담 세금·보험 등 포함 여부를 정책으로 설정
- **기타 조정**: 수수료, 정산 차이, 이월, 관리자가 승인한 조정분

결산 숫자를 별도 입력해 관리하지 않는다. 원장이 변경되면 아직 마감되지 않은 결산은 자동 재계산한다. 마감된 결산은 스냅샷과 버전을 보존하고, 수정이 발생하면 재오픈 또는 조정 분개 절차를 거친다.

### 10.2 일간 결산

매일 영업 종료 후 자동 생성한다.

- 총매출, 순매출, 취소·환불
- 카드·현금·기타 결제수단별 매출
- 당일 지출과 지출 증빙 완료율
- 카드 승인내역 중 미증빙 건
- 매출 시스템과 실제 정산액 차이
- 당일 매출 대비 지출 및 영업 기여금
- 확인이 필요한 예외 목록

정상 건은 자동 마감 후보로 처리하고 차액, 미증빙, 중복 의심, 동기화 실패가 있을 때만 관리자에게 알린다.

### 10.3 주간 결산

사업장 설정에 따른 주 시작일 기준으로 자동 집계한다.

- 일별 매출·지출 추이와 전주 대비 증감
- 주요 지출 계정과목 및 거래처
- 미처리 증빙과 카드 미매칭 누적
- 취소율, 객단가, 인건비 포함 손익 추정
- 이상 지출 및 반복 지출 변화

이미 확정된 일간 결산의 합과 주간 원장 재집계가 다르면 `정합성 오류`로 표시한다.

### 10.4 월간 결산

- 월 순매출, 매출원가/지출, 인건비, 영업이익 추정
- 부가세 공급가액·세액 집계
- 카드사/계좌별 지출 및 결제 예정액
- 증빙 완료율, 미증빙·검토대기·동기화 실패
- 전월/전년 동월 비교
- 세무사 전달용 요약 및 증빙 목록
- CSV/Excel 내보내기와 결산 잠금

월 마감 전 필수 검증 조건을 둔다. 미처리 건이 있어도 권한자가 사유를 남기고 마감할 수 있지만, 누락 목록은 결산 스냅샷에 포함한다.

### 10.5 연말 결산

- 연간 월별 매출·지출·영업이익 추이
- 계정과목·거래처·카드별 연간 합계
- 부가세 및 세무 전달 자료의 월별 완결성
- 미증빙, 중복 제외, 조정 내역, 재오픈 이력
- 연간 급여/인건비 합계
- 전년 대비 증감과 사업장별 비교
- 회계/세무용 원장 및 증빙 인덱스 내보내기

연말 결산은 12개 월 마감 상태를 검사하고 미마감 월, 변경된 원장, 누락 증빙을 먼저 보여준다.

### 10.6 결산 상태와 실행 시점

결산 상태는 `집계 중 → 확인 필요/마감 가능 → 마감 → 재오픈`으로 둔다.

- 일간: 영업 종료 후 자동 집계, 다음 날 관리자 예외 확인
- 주간: 설정된 주 마지막 날 다음 새벽 자동 생성
- 월간: 익월 1일 초안 생성, 설정된 마감일까지 자동 보정
- 연말: 12월 월마감 완료 후 초안 생성

각 결산은 `period_type`, `period_start`, `period_end`, `version`, `source_cutoff_at`, `status`, `summary jsonb`, `closed_by`, `closed_at`을 가진다.

## 11. 카드내역·영수증 중복 방지 설계

### 11.1 하나의 지출, 여러 원천자료

카드 승인내역과 영수증은 서로 다른 지출을 만들지 않는다. 둘 다 `expense_sources`로 먼저 저장한 뒤 매칭되면 하나의 `expenses` 행을 공유한다.

```text
카드 승인내역 ─┐
               ├─ expense_sources ─ expense(지출 1건)
영수증 사진  ──┘
```

영수증만 먼저 들어오면 임시 지출을 생성할 수 있다. 이후 카드내역이 동기화되면 새 지출을 만들지 않고 기존 임시 지출에 연결한다. 카드내역이 먼저 들어오면 미증빙 지출 후보를 만들고, 나중에 영수증이 들어오면 해당 건에 붙인다.

### 11.2 중복 차단 키

- 카드 승인내역: 카드 제공자의 고유 거래 ID를 최우선 고유키로 사용
- 보조키: 조직 + 카드 + 승인번호 + 승인일시 + 금액
- 영수증 파일: 원본 파일 SHA-256 해시
- 영수증 내용: 사업자번호/정규화 상호 + 거래일시 + 합계금액 + 승인번호
- 수기 지출: 같은 날짜·금액·거래처가 존재하면 저장 전 경고

DB unique constraint와 서버의 멱등 키를 함께 사용한다. 프런트엔드 경고만으로 중복을 막지 않는다.

### 11.3 병합 규칙

- 카드 거래 ID가 같으면 무조건 동일 원천으로 판단하고 재삽입하지 않는다.
- 승인번호·금액·카드 끝 4자리·날짜가 일치하면 자동 병합한다.
- 승인번호가 없고 금액·가맹점·시간만 유사하면 자동 병합하지 않고 후보로 제시한다.
- 영수증 재촬영본은 이미지 해시가 달라도 핵심 필드가 같으면 중복 후보로 묶는다.
- 취소 승인은 원결제에 연결하되 원결제를 삭제하지 않고 반대 금액 거래로 기록한다.
- 한 장의 영수증을 여러 카드로 나눈 경우와 여러 영수증을 한 번에 승인한 경우는 N:M 연결을 허용한다.
- 병합과 병합 해제는 감사 로그에 기록하고 언제든 복구할 수 있어야 한다.

### 11.4 결산 반영 규칙

결산은 `expenses`의 확정 금액을 한 번만 합산한다. 연결된 카드내역과 영수증 금액을 각각 더하지 않는다. 원천자료는 금액 산출 대상이 아니라 증명·대조 데이터로만 사용한다.

## 12. 관리자 리소스 최소화

### 12.1 예외 중심 업무함

관리자 홈에는 전체 거래가 아니라 다음 예외만 보여준다.

- OCR 신뢰도가 낮거나 금액 계산이 맞지 않는 영수증
- 카드와 매칭되지 않은 증빙/승인내역
- 중복 가능성이 있는 건
- 매출·정산 차액
- 동기화 실패
- 마감일까지 남아 있는 필수 확인 건

정상 건은 자동 분류·자동 매칭·자동 결산 초안으로 처리한다.

### 12.2 학습형 자동화

- 같은 가맹점에 관리자가 선택한 계정과목과 사유를 다음 거래에 제안
- 카드별 기본 지출자와 계정과목 설정
- 반복 결제 자동 식별
- 사업장별 소액 자동 확정 한도 설정
- 이전 수정 이력을 규칙 후보로 만들되 관리자 승인 후 활성화

### 12.3 대량 처리

- 여러 영수증 한 번에 촬영/업로드
- 여러 건 계정과목·사유·담당자 일괄 적용
- 신뢰도 높은 추천 전체 승인
- 월말 미증빙 대상자에게 일괄 알림
- 카드/매출 동기화와 결산 초안 자동 스케줄

### 12.4 알림 최소화

건별 알림을 기본으로 보내지 않는다. 일간 요약과 마감 임박 요약으로 묶고, 고액 지출·중복 의심·동기화 장기 실패처럼 즉시 조치가 필요한 항목만 실시간 알림을 보낸다.

### 12.5 관리자 대시보드 권장 지표

- 오늘 처리 필요 건수
- 이번 달 매출/지출/영업이익 추정
- 증빙 완료율
- 카드 미매칭 금액
- 마감 가능 여부와 차단 사유
- 마지막 매출·카드 동기화 시각

## 13. 보안·운영 기준

- Storage는 비공개 버킷과 짧은 만료의 signed URL 사용
- 이미지와 OCR 텍스트는 조직 단위 접근 통제
- Vision/LLM 전송 데이터 최소화 및 공급자 보존 정책 확인
- 카드번호 전체, CVC, 인터넷뱅킹 비밀번호 저장 금지
- 삭제는 원장/감사 정책에 따라 논리 삭제 후 보존기간 만료 시 원본 파기
- 재처리 횟수, OCR/LLM 비용, 평균 처리시간, 실패율, 필드별 수정률 측정
- 프롬프트·모델·스키마 버전을 처리 이력에 기록

## 14. 기존 코드 영향

현재 구현은 `timefit_user_finance_documents`와 `timefit-finance-documents` 비공개 버킷에 PDF/CSV/Excel만 저장하며 관리자만 열람·삭제할 수 있다. 다음 변경이 필요하다.

- 메뉴명을 `세금 · 전표`에서 `지출 · 증빙`으로 변경하고 하위 탭 추가
- 기존 테이블/버킷은 정산 자료용으로 유지해 마이그레이션 위험 최소화
- 영수증 이미지를 위한 별도 버킷 또는 기존 버킷 MIME 확장
- OCR 처리용 Edge Function과 비동기 job 테이블 추가
- 지출/카드/매칭/감사 테이블과 RLS 추가
- 매출·지출 통합 결산 스냅샷과 재계산 작업 추가
- 카드와 영수증이 하나의 지출을 공유하는 `expense_sources` 연결 계층 추가
- 기존 `FinanceDocuments`를 하위 화면으로 분리하고 지출 모듈을 독립 컴포넌트로 구성

- 휴대폰 카메라 촬영, 사진 미리보기, 다시 촬영

- Google Cloud Vision을 통한 영수증 사진의 전체 텍스트 변환
- Vision OCR 원문과 위치 정보 저장 및 원본 사진 비교 보기
- LLM JSON 구조화와 서버 검증
- 원본/추출 결과 비교 검수
- 지출 원장 확정·수정·삭제 및 감사 로그
- 카드 CSV/Excel 업로드와 수동/추천 매칭
- 카드/영수증 중복 차단 키와 병합 처리
- 기존 Toss Place 매출 원장 연동
- 일간·주간·월간 결산 초안과 예외 업무함

### 2차

- 반복 가맹점 자동 분류 규칙

- 비용 분석 및 예산 비교

## 16. 완료 기준

- 정상 영수증 20종에서 필수 필드 추출 성공률과 필드별 수정률을 측정할 수 있다.
- 업로드 중복, OCR 실패, 잘린 사진, 다중 영수증, 해외 영수증을 복구할 수 있다.
- AI 결과가 검증 없이 확정 원장을 덮어쓰지 않는다.
- 카드 승인·취소·부분 취소가 중복 없이 동기화된다.
- 지출과 카드 내역의 연결·해제 이력이 남는다.
- 다른 사업장 데이터와 파일에 접근할 수 없음을 RLS 테스트로 확인한다.
- 월별 검색/필터/내보내기 결과가 원장 합계와 일치한다.
- 같은 카드 결제의 카드내역과 영수증이 결산에 한 번만 합산된다.
- 일간 합계, 주간 합계, 월간 원장 재집계 결과가 일치한다.
- 매출 취소·카드 승인 취소·지출 수정이 미마감 결산에 자동 반영된다.
- 관리자는 정상 거래가 아니라 예외 업무함만 처리해 결산을 완료할 수 있다.

## 17. 구현 전 확정할 제품 정책

- 일반 직원도 본인 영수증을 제출할지, 관리자만 사용할지
- 지출 확정 전에 결재를 필수로 할지
- 법인카드 실시간 연동의 우선 카드사와 데이터 제공 방식
- 증빙 원본 및 OCR 텍스트 보존 기간
- 회계 계정과목을 고정 목록으로 운영할지 사업장별 설정으로 둘지
- 일간 영업 마감 시각과 주 시작 요일
- 소액 지출 자동 확정 사용 여부와 금액 한도
- 월마감 후 수정 시 재오픈 권한과 승인 절차

추천 기본값은 **직원 제출 가능, 관리자 확정, 결재는 선택, 계정과목은 사업장별 설정, 카드 연동 전 CSV MVP**다.

## 19. 주요 API 경계

클라이언트가 외부 OCR·LLM·카드 API를 직접 호출하지 않도록 다음 서버 경계를 둔다.

- `POST /expense-documents/upload-session`: 업로드 경로와 문서 ID 발급
- `POST /expense-documents/{id}/process`: OCR/AI 비동기 작업 시작 또는 재시도
- `GET /expense-documents/{id}`: 처리 상태, 원본 미리보기, 추출 결과 조회
- `PATCH /expense-documents/{id}/extraction`: 사용자 교정 내용 임시 저장
- `POST /expense-documents/{id}/confirm`: 지출 확정 또는 기존 지출과 병합
- `POST /card-imports`: 카드 CSV/Excel 가져오기
- `POST /card-connections`: 카드 데이터 제공자 연결 시작
- `POST /card-connections/{id}/sync`: 승인내역 동기화 요청
- `GET /expense-match-suggestions`: 카드·증빙 매칭 후보 조회
- `POST /expense-matches`: 연결 확정
- `DELETE /expense-matches/{id}`: 연결 해제
- `GET /closeouts`: 기간별 결산 조회
- `POST /closeouts/{id}/close`: 결산 마감
- `POST /closeouts/{id}/reopen`: 권한·사유 확인 후 재오픈

외부 연동과 시간이 오래 걸리는 작업은 즉시 작업 ID를 반환하고, 화면은 상태 조회 또는 실시간 구독으로 완료를 반영한다.

## 20. 화면별 빈 화면·오류 처리

- **첫 사용**: 영수증 촬영과 카드내역 가져오기 중 선택할 수 있는 시작 안내
- **OCR 실패**: 원본은 유지하고 `다시 분석`과 `직접 입력` 제공
- **카드 동기화 실패**: 기존 데이터는 유지하고 실패 시각·원인·재연결 제공
- **매출 연동 없음**: 지출 기능은 계속 사용할 수 있고 결산에는 매출 연동 필요 배지 표시
- **중복 의심**: 두 자료를 비교한 뒤 `기존 건에 연결` 또는 `별도 지출` 선택
- **미증빙 카드 건**: 담당자 지정, 제출 요청, 업무상 제외 기능 제공
- **마감 차단**: 막연한 오류 대신 미증빙 N건, 동기화 실패 N건처럼 해결할 항목을 직접 연결

## 23. 최종 출시 게이트

다음 조건을 만족하기 전에는 운영 환경에서 자동 확정을 활성화하지 않는다.

1. 카드내역과 영수증이 연결된 거래가 결산에 한 번만 반영된다.
2. 같은 파일 재업로드와 같은 카드 승인내역 재동기화가 중복 행을 만들지 않는다.
3. 원본, OCR 결과, AI 결과, 사용자 수정, 확정값을 모두 추적할 수 있다.
4. 매출 취소·카드 취소·지출 변경이 미마감 결산에 정확히 반영된다.
5. 마감 결산은 원장 변경으로 조용히 바뀌지 않고 재오픈 이력이 남는다.
6. 조직 간 파일과 지출 데이터 격리가 RLS 자동 테스트를 통과한다.
7. Vision/LLM/카드 연동 실패 시 데이터 유실 없이 재시도할 수 있다.
8. 관리자가 예외 업무함만 처리해 월마감을 완료할 수 있다.

이 문서를 v1 구현의 단일 기준으로 사용하며, 카드 API 제공사·보존기간·결재 필수 여부처럼 외부 계약 또는 운영정책에 의존하는 항목만 구현 전에 별도로 확정한다.

## 24. Granter 드라이브 비교 분석

### 24.1 직접 확인 범위

2026-09-10 로그인된 `버터빌라` 워크스페이스의 Granter 드라이브 화면을 읽기 전용으로 확인했다. 화면에서 확인한 기능은 다음과 같다.

- `새로 만들기` 진입점
- 파일 선택 및 드래그앤드롭 업로드
- 빈 폴더 안내
- 현재 참여자와 추가 참여자 표시
- 우측 협업/활동 패널
- 업로드·삭제 행위의 사용자명, 파일명, 날짜별 활동 기록
- 파일 활동과 연결된 메시지 입력 영역
- 드라이브 사용 가이드 연결

아래 비교에서 Granter의 세부 내부 처리나 화면에서 노출되지 않은 기능은 단정하지 않는다. 실제 화면에서 확인 가능한 사용자 경험을 기준으로 평가한다.

### 24.2 기능 비교

### 24.3 Granter의 강점

1. **낮은 진입장벽**: 파일 선택과 드래그앤드롭이 명확하고 빈 화면에서도 다음 행동을 알 수 있다.
2. **협업 맥락**: 참여자, 메시지 입력, 파일 활동이 같은 화면에 있어 누가 무엇을 했는지 바로 파악할 수 있다.
3. **행위 가시성**: 업로드와 삭제가 날짜별 활동으로 남아 책임 소재와 변경 흐름을 확인하기 쉽다.
4. **제품 전체 연결성**: 드라이브가 계좌, 세금계산서, 현금영수증, 사유작성, 결재 같은 재무 업무 메뉴와 같은 워크스페이스에 있다.
5. **사용 지원**: 기능 화면에서 가이드로 바로 이동할 수 있다.

### 24.4 Granter 대비 관찰된 약점과 기회

1. **파일 중심 구조**: 드라이브 화면만으로는 파일이 어떤 카드 거래, 지출, 계정과목, 결산에 반영되는지 즉시 알기 어렵다.
2. **활동 로그 과밀 가능성**: 반복 업로드·삭제가 메시지 피드에 모두 쌓이면 실제 확인해야 할 요청과 오류가 묻힐 수 있다.
3. **예외 우선순위 부족**: 단순 활동 기록과 처리가 필요한 업무가 한 피드에서 경쟁한다.
4. **증빙 품질 상태 부족**: OCR 성공 여부, 추출 신뢰도, 중복 의심, 카드 매칭 여부가 파일 목록의 핵심 상태로 드러나지 않는다.
5. **결산 영향의 비가시성**: 파일을 추가하거나 삭제했을 때 어느 결산 숫자에 영향을 주는지가 드라이브 화면에서 직접 보이지 않는다.

이 항목들은 Granter 전체 제품에 기능이 없다는 의미가 아니라, 확인한 드라이브 화면에서 사용자가 즉시 파악하기 어려운 지점이며 TimeFit이 더 명확하게 설계할 기회다.

## 25. TimeFit의 경쟁력 설계

### 25.1 파일 보관함이 아닌 증빙 자동화함

TimeFit은 파일을 폴더에 넣는 것으로 작업을 끝내지 않는다. 업로드 즉시 OCR, 구조화, 지출 생성, 카드 매칭, 결산 반영까지 한 흐름으로 진행한다. 사용자가 파일을 어디에 분류할지 고민하지 않아도 시스템이 거래일과 조직을 기준으로 자동 귀속한다.

### 25.2 원본에서 결산 숫자까지 추적

모든 확정 지출 상세 화면에서 다음 경로를 양방향으로 탐색할 수 있어야 한다.

`원본 영수증 → Vision 텍스트 → AI 추출값 → 사용자 수정 → 카드 승인내역 → 지출 원장 → 일/주/월/연말 결산`

결산 숫자를 누르면 구성 거래가 나오고, 거래를 누르면 원본 영수증까지 도달한다. 이것이 일반 드라이브와 TimeFit 재무 운영 제품의 가장 큰 차별점이다.

### 25.3 업무 피드와 감사 로그 분리

- **업무함**: 지금 사람이 해결해야 하는 항목만 표시
- **댓글**: 해당 거래 또는 결산에 관한 협업 대화
- **감사 로그**: 시스템과 사용자의 모든 변경 이력

업로드·삭제 같은 기계적 활동을 대화 피드에 계속 노출하지 않고 감사 로그에 보관한다. 업무함에는 `김나희님의 33,000원 영수증이 카드와 매칭되지 않음`처럼 행동 가능한 문장만 표시한다.

### 25.4 직원 제출 경험

직원에게 복잡한 재무 화면을 보여주지 않는다.

1. 영수증 촬영
2. 지출 목적 선택 또는 음성/짧은 메모
3. 제출

상호, 날짜, 금액, 카드, 계정과목은 시스템이 채우고 직원은 오류가 있을 때만 수정한다. 제출 완료 후에는 `처리 중`, `확인 필요`, `완료`만 단순하게 보여준다.

### 25.5 관리자 완성도 기준

- 오늘 처리할 예외가 첫 화면에 보인다.
- 각 예외에는 원인과 추천 행동이 있다.
- 파일·거래·결산 화면 사이에서 동일 정보를 다시 입력하지 않는다.
- 자동 매칭 근거와 신뢰도를 설명할 수 있다.
- 잘못된 자동화는 한 번에 되돌릴 수 있다.
- 마감 숫자의 출처를 원본 증빙까지 추적할 수 있다.

## 27. 최종 제품 포지셔닝

Granter가 `기업 재무 데이터를 수집·분류·분석하고 협업하는 AI 재무회계 워크스페이스`라면, TimeFit은 다음과 같이 포지셔닝한다.

> **직원이 영수증만 찍으면 카드와 매출을 대조하고, 관리자는 예외만 확인하여 일간부터 연말까지 결산하는 매장 운영 자동화 서비스**

### 29.3 Granter의 제품 약점과 TimeFit의 공략 지점

- 범용 재무 기능이 넓어 소규모 매장 점장에게는 설정과 메뉴 학습 부담이 클 수 있다.
- 데이터 연동과 인증서가 준비되지 않으면 많은 화면이 0원·빈 상태가 되어 초기 가치 도달이 느릴 수 있다.
- 근무·휴가 기능은 현재 확인한 워크스페이스에서 입사일 온보딩 단계였고, TimeFit처럼 태블릿 현장 출퇴근부터 스케줄·휴가·급여까지 검증된 흐름은 화면상 확인되지 않았다.
- 재무 수치는 강하지만 오늘 어느 직원 배치가 매출과 인건비에 어떤 영향을 주었는지까지 연결하는 매장 운영 관점은 TimeFit이 더 깊게 제공할 수 있다.
- 강력한 사용자 정의는 장점인 동시에 관리자가 분류 체계를 계속 관리해야 하는 비용이 된다. TimeFit은 업종 기본값과 자동 추천으로 이를 줄여야 한다.

```text
└─ 알림·세무 공유
```

대시보드는 Granter처럼 모든 데이터를 나열하기보다 `오늘 처리할 일`, `오늘의 손익`, `운영 위험`을 우선한다. 세부 재무 분석은 재무/결산 안으로 이동한다.

## 32. TimeFit만의 핵심 지표

Granter의 재무지표에 다음 매장 운영지표를 결합한다.

- 시간대별 매출 대비 배치 인건비
- 직원/직군별 근무시간과 매출 기여 구간
- 스케줄 인건비 예산 대비 실제 인건비
- 매출 대비 식재료·소모품·인건비 비율
- 휴가/결근/지각으로 발생한 대체 인건비
- 영업시간당 공헌이익
- 메뉴 매출과 관련 매입/원가 추정
- 점장 처리시간 절감량과 자동 처리율

이 지표는 범용 회계 프로그램이 만들기 어려우며, TimeFit의 근무·스케줄·급여·POS 데이터를 결합할 때 가장 강한 방어력이 생긴다.

## 33. 재정의된 최종 우선순위

1. **신뢰 기반**: 통합 원장, 중복 방지, 감사 이력, 조직 격리
2. **입력 자동화**: 영수증 촬영, Vision OCR, LLM 구조화, 카드 매칭
3. **매장 일손익**: POS 매출 + 지출 + 실제 인건비의 일간 결산
4. **관리자 예외함**: 정상 건 자동처리, 해결할 항목만 한곳에 노출
5. **주·월·연말 마감**: 스냅샷, 잠금, 재오픈, 세무 전달
6. **재무 깊이**: 거래처, 계좌, 자금일보, 고정비, 태그, 결재
7. **확장성**: 다중 판매채널, 재고, 자산/부채, 외부 전문가 생태계

완성도 판단 기준은 Granter와 같은 메뉴 수가 아니다. 매장 관리자가 출퇴근·스케줄·급여·매출·영수증을 각각 대조하던 시간을 얼마나 줄이고, 하루 손익을 얼마나 빠르고 신뢰성 있게 마감하는지가 기준이다.
