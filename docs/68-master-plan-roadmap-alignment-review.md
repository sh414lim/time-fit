## 1. 최종 판정

**조건부 승인 — 구현 착수 가능, 외부 API 실연동은 하이픈 명세·계약 확인 후 확정**

로드맵은 총기획의 핵심 목표를 대부분 실행 가능한 구조로 변환했다. 특히 법인카드 자동 연결, 보유카드 자동 등록, 승인·취소·매입 자동조회, 영수증 촬영/OCR, 단일 지출 원장, 중복 방지, 결산 스냅샷은 서로 일관된다.

다만 다음 세 종류의 보완이 필요하다.

1. 하이픈 실제 필드·인증·과금 단위가 미확정이므로 adapter 경계를 유지해야 한다.
2. 승인 이메일, 권한, 알림, 결산 세부 산식은 개발 티켓 단계에서 더 분해해야 한다.
3. 총기획의 후속 기능인 세금계산서·현금영수증·계좌·재고는 현재 핵심 릴리스 범위 밖임을 명시해야 한다.

검토 과정에서 발견한 총기획의 Release 순서 충돌은 수정했다. 이제 두 문서 모두 `카드 원장 기반 → 하이픈 자동 연결 → 영수증 OCR → 결산` 순서로 정렬되어 있다.

## 3. 정합성이 높은 부분

### 제품 목표

두 문서 모두 범용 회계 ERP가 아니라 매장 운영 자동화를 목표로 한다. 카드 거래, 영수증, 매출, 실제 인건비를 결합하고 관리자가 정상 건 전체가 아닌 예외만 처리한다는 중심 가치가 유지됐다.

### 카드 구조

총기획의 `카드내역과 영수증은 각각 지출이 아니다`라는 원칙이 로드맵의 다음 구조로 정확히 변환됐다.

```text
외부 원천 이벤트
→ 카드 거래 그룹
→ 영수증/원천 매칭
→ 확정 지출 원장 1건
→ 결산 1회 반영
```

이 구조는 승인, 취소, 매입을 단순 행 목록으로 저장하는 현재 구현보다 실제 금융 데이터에 적합하다.

### 자동 연결과 폴백

자동 연결이 주기능이고 CSV·이메일은 보조 수단이라는 우선순위가 일치한다. API가 끊겨도 이미 수집한 원장과 마감 결산을 유지하고 CSV로 이어갈 수 있어 운영 중단 위험이 낮다.

### OCR 안전성

Vision은 문자 인식, LLM은 구조화, 코드는 금액·날짜·사업자번호 검증을 담당한다. AI가 회계 숫자를 단독 확정하지 않도록 책임이 분리되어 있다.

### 출시 통제

두 문서 모두 자동 확정을 기본 OFF로 하고, 2주간 API/CSV 대조, 오합산 0건, 조직 격리, 인증정보 보안 조건을 출시 기준으로 둔다.

## 4. 발견된 차이와 조치

### A. Release 순서 충돌 — 조치 완료

총기획 상단 Phase는 하이픈 연결이 OCR보다 앞이었지만 하단 Release A에는 OCR이 포함되어 있었다. Release를 다음과 같이 수정했다.

```text
Release A 카드 원장·폴백
Release B 하이픈 자동 연결
Release C 영수증 촬영·OCR·매칭
Release D 제한 운영·출시
```

### B. 승인 이메일 구현 깊이 — 보완 필요

총기획은 사업장별 전용 주소, DKIM/SPF, 카드사별 파서를 요구한다. 로드맵에는 Email Provider 골격만 있다.

개발 티켓에 다음을 추가한다.

- 조직별 수신 alias와 검증된 forwarding 등록
- inbound email webhook의 서명 검증
- SPF/DKIM/DMARC 결과와 허용 발신자 정책
- Message-ID·첨부 SHA 기반 중복 차단
- 카드사/템플릿 버전별 parser fixture
- 원문 최소 보존과 개인정보 마스킹
- 파싱 실패 예외함과 관리자 재처리

이 기능은 카드사 API를 대체하는 회계 원천이 아니라 빠른 승인 후보와 장애 폴백이다.

### C. 권한 상세 — 보완 필요

총기획에는 역할표가 있지만 로드맵은 소유자/관리자 수준만 기술했다. 구현 시 다음 권한을 별도 permission으로 분리한다.

- `expense.submit_own`
- `expense.view_own`
- `expense.review_all`
- `expense.confirm`
- `card.view_transactions`
- `card.manage_assignments`
- `card.manage_connection`
- `closeout.view`
- `closeout.close`
- `closeout.reopen`
- `finance.export`

카드 연결·재인증·해제는 소유자만, 거래 검수는 위임받은 관리자까지 허용한다.

### D. 결산 산식 — 티켓 분해 필요

로드맵에 결산 테이블과 화면은 있으나 총기획의 일간·주간·월간 항목이 계산 규칙 단위로 충분히 분리되지 않았다.

반드시 결정할 정책:

- 한국 시간 기준 영업일 cutoff와 심야 영업 귀속
- 승인액/매입액 중 월 결산 기준
- 승인월과 매입월이 다른 거래 처리
- POS 주문일/정산일/입금일의 구분
- 예상 인건비와 확정 급여의 표기·교체 시점
- 부가세 포함/별도/면세·불공제 처리
- 마감 후 취소의 재오픈 또는 다음 기간 조정
- 주 시작 요일과 53주차 처리

권장 기본값은 운영 화면은 승인 기준 잠정치, 월마감은 매입 기준 확정치다.

### E. 자동화 규칙 — 범위 명확화 필요

총기획은 같은 가맹점의 계정과목·사유 재사용과 반복 결제를 요구한다. 로드맵 Sprint 5에 있으나 rule engine의 우선순위가 없다.

권장 우선순위:

```text
관리자 거래별 확정값
→ 카드별 기본값
→ 거래처 명시 규칙
→ 조직 자동화 규칙
→ AI 추천
→ 미분류
```

규칙 변경은 미래 거래 기본 적용이며 과거 거래 일괄 적용은 미리보기와 명시적 확인을 요구한다.

### F. 세무 기능 경계 — 명확화 필요

총기획의 연말 결산과 세무사 전달은 자료 집계·내보내기 범위다. 부가세·법인세 신고, 회계 전표 자동 생성, 국세청 제출까지 포함한다고 해석하면 일정이 크게 달라진다.

1차 출시 범위를 다음으로 제한한다.

- 증빙 인덱스
- 카드/거래처/계정과목별 합계
- 공급가액·부가세 추출값
- 미증빙·조정·재오픈 목록
- Excel/ZIP 내보내기

세금 신고 적격성 판단과 전자신고는 후속 회계/세무 연동 범위다.

### G. 후속 Granter 대응 기능 — 의도적 제외

계좌, 세금계산서, 현금영수증, 재고, 전자결재, 자산 변동은 총기획 Phase 6 또는 별도 제품 확장이다. 현재 14주 핵심 로드맵에 넣지 않는다.

이들을 동시에 구현하면 카드 자동 연결과 OCR의 출시가 지연되고 품질 검증이 약해진다. 첫 출시 후 사용자 데이터로 우선순위를 다시 정한다.

## 5. 현재 프로젝트와의 적합성

### 재사용 가능

- Supabase Auth와 조직 RLS
- 비공개 finance document Storage 구조
- Vercel Functions와 Cron
- Toss Place 서버 연동 패턴
- AES-256-GCM 비밀정보 암호화 유틸리티
- 급여·매출 데이터와 관리자 메뉴

### 교체·확장 필요

- `timefit_user_corporate_cards`의 `unique(organization_id, issuer, last4)`는 동일 끝4자리 카드 충돌 가능성이 있어 provider card ID 기반으로 변경
- `timefit_user_card_transactions`의 approval/cancellation 2상태를 event/group 모델로 확장
- 브라우저가 카드 거래를 직접 upsert하는 현재 구조를 서버 수집·정규화 구조로 이전
- 카드 삭제 시 거래 cascade 삭제 정책을 연결 해제·과거 원장 유지 정책으로 변경
- 현재 finance documents를 영수증 처리 상태·OCR 실행·지출 source 모델과 연결
- 테스트 runner 부재를 해결하기 위해 Vitest/React Testing Library/Playwright 도입

카드 삭제 cascade는 출시 전에 반드시 고쳐야 하는 가장 큰 데이터 보존 위험이다.

## 6. 일정 검토

로드맵의 개발 14주와 Pilot 2주는 2명 전담, 하이픈 명세가 Sprint 0에 확보된다는 조건에서 가능하다.

| 조건 | 예상 |
|---|---:|
| 2명 전담·명세 즉시 확보 | 개발 14주 + Pilot 2주 |
| 1명 전담 | 개발 18~22주 + Pilot |
| 하이픈 인증 방식 커스텀 개발 | 별도 2~4주 위험 버퍼 |
| 다수 카드사별 예외 대응 | 카드사당 fixture/QA 추가 |
| 세무 신고·계좌·세금계산서 동시 포함 | 현재 로드맵 재산정 필요 |

가장 큰 일정 위험은 UI가 아니라 하이픈 계약, 카드사 인증 방식, 원승인/취소 연결 필드, 호출 제한이다.

## 8. 최종 승인 조건

다음 조건을 모두 만족하면 개발 로드맵을 확정 실행안으로 승인한다.

1. 하이픈 테스트베드와 명세를 확보한다.
2. 핵심 카드사의 인증 방식과 지원 범위를 확인한다.
3. 카드 비밀번호·인증서 비밀번호를 TimeFit이 평문 장기 보관하지 않는다.
4. 기존 카드 데이터의 무손실 이관과 rollback이 준비된다.
5. 카드 삭제 cascade를 과거 원장 보존 방식으로 바꾼다.
6. 승인·부분취소·매입을 하나의 거래로 합성한다.
7. 같은 데이터의 API·CSV·이메일 재유입에도 합계가 변하지 않는다.
8. 영수증 OCR 오류가 자동 확정으로 이어지지 않는다.
9. 마감 결산이 사후 동기화로 조용히 바뀌지 않는다.
10. API/CSV 2주 병행 대조에서 오합산 0건을 달성한다.

## 9. 결론

총기획과 로드맵은 핵심 방향에서 정합하다. 개발 착수 순서는 다음으로 고정한다.

```text
외부 명세·계약
→ 데이터 보존 위험 제거
→ 카드 이벤트/지출 원장
→ 카드 자동 연결·조회
→ 영수증 촬영·OCR·매칭
→ 예외 업무함
→ 통합 결산
→ 2주 병행 검증
→ 제한 출시
```

첫 번째 기술 완료 기준은 화면이 보이는 것이 아니라, **실제 테스트 카드 한 장의 보유카드·승인·취소·매입 내역이 자동 수집되고 CSV와 합계가 일치하며 재수집에도 중복이 생기지 않는 것**이다.
