# TimeFit 자체 카드 Provider 최종 기획 검토 및 사용 시나리오

## 1. 최종 검토 판정

기획은 **조건부 승인**한다. 현재 TimeFit의 조직·카드·거래 이벤트·지출 원장 구조 위에 카드사별 인증 Connector와 비동기 수집 엔진을 추가하는 방향은 기술적으로 타당하다. 다만 첫 카드사에 대한 인증 POC와 카드사 CSV 대사가 완료되기 전에는 개발 완료 또는 상용 연동으로 표시하지 않는다.

제품의 핵심 정의는 다음과 같다.

> TimeFit 자체 카드 Provider는 고객 회사의 명시적 동의와 인증을 받아 카드사별 Connector로 보유 법인카드와 거래내역을 수집하고, 승인·취소·매입을 회사별 지출 원장으로 변환하는 내부 금융 데이터 수집 플랫폼이다.

필수 조건:

1. 전체 과정이 TimeFit 화면 안에서 진행된다.
2. 하이픈·쿠콘 같은 외부 Provider에 종속되지 않는다.
3. 카드사마다 독립 Connector를 구현한다.
4. 전체 카드번호·CVC·결제 비밀번호는 저장하지 않는다.
5. 인증정보는 일반 DB가 아닌 Vault에 보관한다.
6. 동기화는 화면 요청과 분리된 Queue/Worker에서 실행한다.
7. 연결 활성화 전에 카드사 CSV와 실제 금액을 대사한다.
8. 회사 간 카드·인증정보·거래가 절대 섞이지 않아야 한다.

## 2. 기획 완성도 검토

| 영역 | 현재 기획 상태 | 보완 후 판정 |
| --- | --- | --- |
| 사용자 연결 흐름 | 정의됨 | 승인 |
| 카드사별 Connector 계약 | 정의됨 | 승인 |
| 인증서·ID/PW 보관 | Vault 방향 정의 | Vault 제품과 운영 정책 결정 필요 |
| 추가 인증 | challenge 상태 정의 | 카드사별 실제 POC 필요 |
| 보유카드 등록 | token+last4 정의 | 승인 |
| 거래 수집 | 승인·취소·매입 정의 | 카드사별 fixture 필요 |
| 중복·부분취소 | 공통 event/group 존재 | 승인 |
| 비동기 실행 | Queue/Worker 설계 | 인프라 선택 필요 |
| 대사 | CSV 기준 정의 | 승인 |
| 권한·테넌트 격리 | 원칙 정의 | 자동 공격 테스트 필요 |
| 운영 대응 | 오류·kill switch 정의 | 운영 콘솔과 당직 정책 필요 |
| 법률·약관 | 질문 정의 | 첫 카드사 착수 전 서면 검토 필요 |

현재 기획상 가장 큰 불확실성은 공동인증서를 TimeFit 서버에서 재사용할 수 있는지, 사용자 PC의 로컬 모듈이 필요한지다. 이는 카드사와 인증 수단별로 달라질 수 있으므로 첫 카드사 POC의 최우선 검증 항목으로 둔다.

## 3. 제품 범위

### 3.1 Pilot 포함

- 법인사업자 회사 1~3곳
- 법인공용카드
- 카드사 1곳
- 공동인증서 또는 기업 ID/PW 인증
- 휴대전화·앱·OTP 추가 인증
- 보유카드 조회와 선택
- 카드 담당 직원·부서·매장 지정
- 최근 90일 승인·취소·부분취소·매입 수집
- 30~60분 승인 증분 동기화
- CSV 업로드와 일별 대사
- 재인증·일시정지·연결 해제
- 직원 사유·영수증 제출
- 관리자 예외 검토

- CVC·결제 비밀번호 수집

- CAPTCHA 우회
- 모든 카드사 동시 지원
- 자동 세무 적격성 확정
- API 외부 판매

### 3.3 후속 확장

- 법인개별카드와 개인사업자 카드

- 이메일 승인 알림
- 카드사 공식 EDI/API 병행
- 모바일 인증서와 로컬 Connector

## 6. 정상 사용 시나리오

### U01. 첫 법인카드 연결

사전조건: 회사 소유자가 TimeFit 조직을 생성했다.

1. 소유자가 `설정 > 금융 연동 > 카드사 연결`을 누른다.
2. 수집 항목, 목적, 주기, 보존기간과 해제 방법을 확인한다.
3. 필수 동의 후 법인사업자를 선택한다.
4. 사업자번호를 입력하고 첫 카드사를 선택한다.
5. 공동인증서 인증을 선택한다.
6. 인증서를 선택하고 비밀번호를 입력한다.
7. TimeFit이 인증서 유효기간과 사업자 식별정보를 검사한다.
8. 카드사 Connector가 기업 고객으로 로그인한다.
9. 보유카드 목록을 조회한다.
10. TimeFit은 카드사·상품명·last4만 표시한다.

완료 기준:

- 동의 전문 hash와 동의자·시각이 남는다.
- 전체 PAN·인증서 비밀번호가 DB와 로그에 없다.
- 연결 상태가 `selecting`으로 전환된다.

### U02. 보유카드 선택과 담당자 지정

1. 비용관리자가 발견된 카드 목록을 확인한다.
2. 자동 수집할 카드를 체크한다.
3. 카드마다 직원, 부서 또는 매장을 지정한다.
4. 담당 적용 시작일을 선택한다.
5. `선택 카드 연결`을 누른다.
6. TimeFit이 corporate card와 assignment history를 생성한다.

완료 기준:

- 동일 카드를 다시 발견해도 중복 생성되지 않는다.
- last4가 같아도 token이 다르면 자동 병합하지 않는다.
- 담당자 적용기간과 변경자가 기록된다.

### U03. 최근 90일 최초 수집

1. 카드 선택 완료 후 TimeFit이 backfill job을 생성한다.
2. 기간을 카드사 제한에 맞게 분할한다.
3. 승인과 매입을 별도 작업으로 수집한다.
4. 페이지마다 cursor와 진행률을 갱신한다.
5. 표준 이벤트를 저장하고 거래 그룹을 생성한다.
6. 지출 원장 초안을 만든다.
7. 화면은 카드별 진행률을 표시한다.

완료 기준:

- 화면을 닫아도 작업이 계속된다.
- 중간 실패 시 완료 페이지를 다시 처리하지 않는다.
- 동일 범위 재실행 후 거래 수와 합계가 동일하다.

### U04. CSV 대사와 연결 활성화

1. 관리자가 카드사 홈페이지에서 같은 기간 파일을 내려받는다.
2. TimeFit 대사 화면에 CSV/XLSX를 업로드한다.
3. TimeFit이 날짜·카드·승인번호·금액을 매핑한다.
4. API 수집 결과와 카드별·일별 건수/순액을 비교한다.
5. 차이가 없으면 대사를 통과시킨다.
6. 연결 상태를 `active`로 변경한다.

완료 기준:

- 30일 이상 일별 순액 100% 일치
- 중복·누락·미결합 취소 0건
- 대사 결과와 파일 hash가 감사 기록에 남음

### U05. 정기 자동 동기화

1. Scheduler가 수집 예정 연결을 조회한다.
2. 카드별 승인·매입 job을 Queue에 생성한다.
3. Worker가 최근 성공 cursor와 overlap 기간을 읽는다.
4. Connector가 신규·변경 이벤트를 조회한다.
5. 기존 idempotency key는 중복으로 제외한다.
6. 성공한 카드 cursor만 전진시킨다.

완료 기준:

- 한 카드 실패가 다른 카드 동기화를 막지 않는다.
- 최근 성공·다음 예정·신규 건수가 화면에 표시된다.
- 동일 이벤트가 지출 금액에 중복 합산되지 않는다.

### U06. 직원의 증빙 제출

1. 신규 승인 거래가 카드 담당 직원에게 표시된다.
2. 직원이 지출 사유, 프로젝트와 태그를 입력한다.
3. 영수증을 촬영하거나 업로드한다.
4. OCR이 금액·날짜·가맹점을 추출한다.
5. TimeFit이 카드 거래와 매칭 점수를 계산한다.
6. 직원이 제출하고 관리자가 확인한다.

완료 기준:

- 직원은 카드사 원본 금액과 일시를 수정할 수 없다.
- 동일 영수증 중복 업로드가 차단된다.
- 제출·수정·확정 이력이 남는다.

## 7. 인증 예외 시나리오

### A01. 잘못된 인증서 비밀번호

1. 인증서 비밀번호 검증에 실패한다.
2. Connector에 요청을 보내기 전에 사용자에게 오류를 표시한다.
3. 남은 시도와 계정 잠금 주의를 표시한다.
4. 입력한 비밀번호를 즉시 폐기한다.

완료 기준: 비밀번호가 로그·분석 도구·오류 body에 남지 않는다.

### A02. 인증서 만료

1. 인증서 유효기간 검사에서 만료가 확인된다.
2. 카드사 로그인 시도를 중단한다.
3. 새 인증서 등록 안내를 표시한다.
4. 기존 연결은 `reauth_required`가 된다.

완료 기준: 자동 재시도로 계정이 잠기지 않는다.

### A03. 휴대전화·앱 추가 인증

1. 카드사 로그인 중 추가 인증 요구를 감지한다.
2. Connector session을 유지하고 challenge를 생성한다.
3. TimeFit modal에서 인증 방법과 제한시간을 표시한다.
4. 사용자가 OTP를 입력하거나 카드사 앱 승인을 완료한다.
5. 같은 session에서 인증을 이어간다.
6. 성공 후 challenge 데이터를 폐기한다.

완료 기준: challenge 만료 후 기존 코드를 재사용할 수 없다.

### A04. 카드사 계정 잠금 위험

1. 연속 인증 실패가 기준을 초과한다.
2. TimeFit이 자동 시도를 즉시 중단한다.
3. 카드사 홈페이지에서 계정 확인하도록 안내한다.
4. 관리자 확인 전까지 연결을 `paused`로 둔다.

### A05. 자동 동기화 중 인증 만료

1. Worker가 인증 오류를 받는다.
2. 같은 credential로 반복 재시도하지 않는다.
3. 연결을 `reauth_required`로 전환한다.
4. 관리자에게 재인증 요청을 보낸다.
5. 재인증 성공 후 실패 cursor부터 수집한다.

완료 기준: 재인증 전 과거 원장과 카드 정보는 유지된다.

## 8. 카드 자산 예외 시나리오

### C01. 신규 발급 카드 발견

1. 일일 카드 목록 동기화에서 새로운 token이 발견된다.
2. 카드를 `discovered` 상태로 저장한다.
3. 관리자에게 신규 카드 연결 여부를 묻는다.
4. 선택 전에는 거래를 자동 원장에 반영하지 않는다.

### C02. 카드 재발급

1. 동일 카드명과 담당자지만 새로운 token이 발견된다.
2. 카드사가 재발급 관계를 제공하면 이전 카드와 연결한다.
3. 관계 정보가 없으면 관리자 확인 대상으로 표시한다.
4. 이전 카드는 과거 거래를 유지하고 inactive 처리한다.

### C03. 동일한 마지막 4자리

1. 두 카드의 last4가 동일하다.
2. token과 카드사 고유 ID로 서로 다른 카드로 유지한다.
3. UI에서 카드명·담당자·발급상태로 구분한다.

### C04. 카드 해지

1. 카드 목록 조회에서 inactive/해지가 확인된다.
2. 신규 수집을 중단한다.
3. 과거 거래·증빙·결산은 삭제하지 않는다.
4. 관리자에게 상태 변경을 알린다.

## 9. 거래 예외 시나리오

### T01. 승인 후 전체취소

1. 100,000원 승인을 수집한다.
2. 이후 100,000원 취소를 수집한다.
3. 승인번호/원승인번호로 같은 그룹에 연결한다.
4. 그룹 상태를 cancelled, 순액을 0원으로 변경한다.

완료 기준: 승인과 취소가 지출 200,000원으로 합산되지 않는다.

### T02. 승인 후 부분취소

1. 100,000원 승인 후 20,000원 부분취소가 발생한다.
2. 원승인 참조로 같은 그룹에 연결한다.
3. 취소 누적액 20,000원, 순액 80,000원으로 표시한다.
4. 영수증 금액이 100,000원이면 차이 예외를 만든다.

### T03. 승인 없이 매입이 먼저 발견

1. 매입 데이터에 대응 승인 이벤트가 없다.
2. 임시 거래 그룹과 `review_required` 지출을 만든다.
3. 추후 승인 수집 시 결합 조건을 다시 계산한다.
4. 확신이 낮으면 관리자가 직접 연결한다.

### T04. 해외 결제 금액 변경

1. 승인 당시 외화 금액과 예상 KRW를 저장한다.
2. 매입 시 최종 환율·수수료·KRW 금액을 받는다.
3. 기존 그룹의 매입 금액을 최종 지출 기준으로 사용한다.
4. 승인 대비 차이를 이력으로 표시한다.

### T05. 중복 수집

1. 최근 7일 overlap으로 기존 승인이 다시 들어온다.
2. provider event ID 또는 idempotency key가 일치한다.
3. 새 event를 만들지 않고 수신 시각만 metric에 반영한다.

### T06. 결산 확정 후 취소

1. 8월 결산을 확정한다.
2. 9월에 8월 거래 취소가 수집된다.
3. 8월 확정 snapshot은 수정하지 않는다.
4. 9월 조정분을 생성하거나 권한 있는 관리자가 8월을 재오픈한다.

## 10. 수집 장애 시나리오

### F01. 카드사 점검

1. Connector가 점검 응답을 식별한다.
2. 연결을 degraded로 표시한다.
3. 카드사 점검 종료 이후로 재실행을 예약한다.
4. 기존 원장에는 영향을 주지 않는다.

### F02. 호출 제한

1. 카드사가 429 또는 제한 오류를 반환한다.
2. Retry-After 또는 카드사별 backoff를 적용한다.
3. 동일 계정 동시 실행을 줄인다.
4. 작업을 실패가 아닌 retry_scheduled로 둔다.

### F03. 5페이지 중 3페이지 실패

1. 1~2페이지 event와 cursor를 저장한다.
2. 3페이지 timeout이 발생한다.
3. 작업을 partial로 기록한다.
4. 재실행 시 3페이지부터 이어간다.
5. 전체 구간 완료 후에만 succeeded-through를 끝 시각으로 전진시킨다.

### F04. 카드사 화면·응답 변경

1. 필수 selector 또는 schema field가 사라진다.
2. 빈 카드/거래 목록을 정상으로 처리하지 않는다.
3. Connector를 `disabled` 또는 `schema_changed`로 차단한다.
4. 운영자에게 fixture와 실패 단계가 포함된 경보를 보낸다.
5. 고객에게 데이터 손실이 아니라 동기화 지연으로 표시한다.

### F05. Worker 중단

1. 작업 처리 중 Worker heartbeat가 끊긴다.
2. lease 만료 후 다른 Worker가 작업을 회수한다.
3. 마지막 확정 cursor부터 재개한다.
4. idempotency key로 이미 저장한 이벤트를 제외한다.

## 11. 보안 시나리오

### S01. 교차 회사 객체 접근

1. 조직 A 관리자가 URL의 connection ID를 조직 B 값으로 변경한다.
2. API가 사용자 membership, 요청 조직과 객체 조직을 다시 확인한다.
3. 403을 반환하고 B의 존재 여부·카드사·last4를 노출하지 않는다.
4. 보안 감사 이벤트를 기록한다.

### S02. 인증정보 로그 유출 방지

1. 인증 중 예외가 발생한다.
2. 오류 logger가 password, certificate, OTP, PAN 필드를 제거한다.
3. 사용자에게는 공통 오류코드와 해결 방법만 표시한다.

### S03. 연결 해제

1. 소유자가 연결 해제를 요청한다.
2. 신규 job 생성을 중단한다.
3. queued/running job을 취소한다.
4. Connector session을 종료한다.
5. Vault credential을 폐기한다.
6. 과거 지출·증빙·결산은 회사 보존정책에 따라 유지한다.

### S04. TimeFit 운영자 지원 접근

1. 고객이 지원 요청과 접근 범위를 승인한다.
2. 시간제한 break-glass 권한을 발급한다.
3. 운영자는 민감 원문 없이 job 상태부터 확인한다.
4. 모든 조회가 감사 로그에 남는다.
5. TTL 종료 시 권한이 자동 회수된다.

## 12. 알림 정책

| 이벤트 | 대상 | 채널 | 반복 정책 |
| --- | --- | --- | --- |
| 추가 인증 필요 | 연결 관리자 | 앱 즉시 | challenge 만료 전 1회 추가 |
| 재인증 필요 | 소유자·비용관리자 | 앱+이메일 | 1일 1회, 최대 3회 |
| 신규 카드 발견 | 비용관리자 | 앱 | 1회 |
| 거래 증빙 요청 | 카드 담당자 | 앱 | 회사 리마인드 정책 |
| 카드사 점검 | 비용관리자 | 앱 상태 | 점검 중 반복 알림 없음 |
| schema 변경 | TimeFit 운영자 | 긴급 경보 | 해결 시까지 incident 관리 |
| 대사 차이 | 비용관리자 | 앱+이메일 | 대사 실행마다 |

기술적 일시 오류를 직원에게 알리지 않는다. 고객이 행동해야 하는 인증·대사·증빙 문제만 알린다.

## 13. 운영 콘솔

운영자가 확인할 항목:

- 카드사별 Connector version과 상태
- 최근 1시간/24시간 성공률
- 인증·점검·429·network·schema 오류율
- Queue 지연과 장기 running job
- 회사별이 아닌 익명화된 카드/호출 수
- 마지막 합성 health check
- 현재 kill switch
- 배포 version과 Git commit

운영자에게 기본적으로 표시하지 않을 항목:

- 인증서·ID·비밀번호
- 전체 카드번호
- 가맹점 상세와 지출 사유
- 영수증 원문

## 14. 성공 지표

제품:

- 카드 연결 시작 대비 인증 완료율
- 인증 완료 대비 카드 discovery 성공률
- 최초 90일 수집 완료 시간
- 거래 수집 후 직원 노출까지의 시간
- 3일 내 증빙 제출률
- 관리자 수동 처리 비율

기술:

- 동기화 성공률 99% 이상
- P95 승인 반영 60분 이하
- 중복 합산률 0%
- CSV 대사 차이율 0%
- schema 변경 오탐으로 인한 삭제 0건
- 교차 조직 노출 0건
- secret/PAN 로그 탐지 0건

## 17. 최종 인수 테스트

1. 신규 회사가 TimeFit 내부에서 첫 카드사를 연결한다.
2. 공동인증서·ID/PW 원문이 일반 DB와 로그에 없다.
3. 보유카드를 중복 없이 발견한다.
4. 여러 카드 중 선택한 카드만 수집한다.
5. 카드 담당자가 올바르게 지정된다.
6. 최근 90일 작업이 화면 종료 후에도 완료된다.
7. 승인·전체취소·부분취소·매입 순액이 정확하다.
8. 동일 범위 반복 수집에도 합계가 변하지 않는다.
9. 일부 page 실패 후 이어서 처리한다.
10. 인증 만료 시 자동 공격 없이 재인증을 요청한다.
11. 카드사 점검과 schema 변경을 구분한다.
12. 신규·재발급·해지 카드를 안전하게 처리한다.
13. 직원은 본인 거래만 조회한다.
14. 조직 A가 조직 B 금융 객체에 접근하지 못한다.
15. CSV와 30일 이상 일별 순액이 일치한다.
16. 결산 후 취소가 확정본을 조용히 변경하지 않는다.
17. 연결 해제 후 신규 카드사 호출이 없다.
18. 운영자 지원 접근이 승인·TTL·감사 조건을 만족한다.
19. production 배포가 Git main commit과 일치한다.
20. Pilot 2주간 P0/P1 결함이 없다.

## 18. 최종 권고

첫 개발 목표는 “공동인증서 화면”이나 “카드 등록 버튼”이 아니다. 첫 번째 실제 성공 단위는 다음과 같다.

```text
카드사 1곳
× Pilot 법인 1곳
× 실제 카드 1~10장
× 인증·추가 인증
× 보유카드 discovery
× 승인·취소·매입 30일
× CSV 대사 100%
× 재인증
```

이 단위가 통과한 뒤 동일 Connector 구조로 카드사를 추가한다. 첫 카드사 POC에서 인증 방식이 약관상 허용되지 않거나 지속 자동화가 불가능하면 해당 카드사는 개발하지 않고 공식 ERP/EDI 또는 CSV 방식으로 전환한다.
