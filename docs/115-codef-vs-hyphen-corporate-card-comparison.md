# TimeFit 법인카드 Provider 비교 분석 — CODEF vs Hyphen

분석 기준일: 2026-09-12

분석 목적: 그랜터와 유사하게 공동인증서 또는 카드사 인증으로 법인카드를 연결하고, 승인·취소·매입 내역을 TimeFit에서 자동 수집하기 위한 주 Provider 선정

## 1. 요약 결론

현재 공개 정보 기준 최종 판단은 다음과 같다.

- 상용 구조 적합도 1순위: CODEF
- 저비용·빠른 Pilot 1순위: Hyphen TR슬림
- 실제 최종 선택: 두 Provider의 Sandbox에서 같은 카드·같은 기간을 수집하고 견적까지 받은 후 결정

그랜터가 CODEF를 이용한다는 사실은 CODEF가 유사한 멀티테넌트 재무SauS에서 실제 활용되고 있다는 강한 참고 사례다. CODEF의 End User별 Connected ID 구조도 TimeFit이 인증정보 대신 불투명 연결 식별자만 저장하려는 설계와 잘 맞는다.

반면 Hyphen은 월 10만 원이라는 공개 진입비와 법인카드 승인·매입 API를 명시해 초기 Pilot의 비용 예측과 착수가 쉽다. 다만 스크래핑 기반이며 건당 정상요금, 인증정보 보관 구조, SaaS 재제공 권한을 계약 전에 확인해야 한다.

권장 전략:

```text
CODEF를 상용 주 후보로 협상
+ Hyphen TR슬림으로 빠른 기술 Pilot 가능성 확보
→ 동일 카드 30~90일 비교
→ 정확도·보안·계약·총원가 점수로 최종 선정
```

## 2. TimeFit의 필수 요구사항

### P0 데이터

- 법인 보유카드 목록
- 승인내역
- 전체취소·부분취소
- 매입내역
- 승인번호와 원승인 연결키
- 카드사, 카드 식별자, last4
- 거래일시, 금액, 가맹점명, 사업자번호
- 페이지네이션과 과거 90일 조회

### P0 운영

- End User/고객사별 연결 식별자
- 인증 만료와 재인증 판별
- 카드사별 오류코드
- 중복되지 않는 Provider event ID
- 호출 제한과 권장 주기
- 테스트베드
- 멀티테넌트 SaaS 제공 권리
- 인증서·비밀번호를 TimeFit DB에 저장하지 않는 방식

## 3. 공개적으로 확인된 사실

### CODEF

- 개인·법인 카드 API 제공
- 보유카드·승인·청구·한도·결제예정 등 제공
- End User 인증수단 등록 후 Connected ID 발급
- 데모와 정식 서비스 구분
- 공식 SDK 제공
- 인증서 relay는 별도 문의
- 그랜터가 금융사 데이터 연동에 CODEF 기술을 사용한다고 공식적으로 공개

공개 자료만으로 확정되지 않은 항목:

- 법인카드 매입 API의 최종 계약 포함 여부
- 부분취소 원승인 연결 필드
- 법인카드 API별 단가
- Connected ID 비용
- 인증서 relay 비용
- TimeFit 하위 고객사 제공 권리

### Hyphen

- 법인카드 조회가 스크래핑 방식이라고 명시
- 보유카드·결제예정·승인·매입·카드번호·한도 API 제공
- 필요한 API만 개별 계약 가능
- Local Scraping, Server Scraping, API 방식 안내
- TR슬림과 TR시그니처 모두 테스트베드 제공
- TR슬림 월 100,000원 + 정상응답 건별 과금
- TR시그니처 월 300,000원부터 + 상품별 기본 건수

공개 자료만으로 확정되지 않은 항목:

- 정상응답 건당 단가
- 무내역·오류·페이지별 과금 여부
- 부분취소 원승인 연결 필드
- 고객 인증정보 보관 방식
- TR슬림의 멀티테넌트 SaaS 재제공 허용 여부
- 카드사별 인증·지원 차이

## 4. 기능 비교

| 평가 항목 | CODEF | Hyphen | 우세 |
|---|---|---|---|
| 법인 보유카드 | 제공 | 제공 | 동등 |
| 승인내역 | 제공 | 제공 | 동등 |
| 매입내역 | 소개 자료/명세 확인 | 명시 제공 | Hyphen 공개성 |
| 취소·부분취소 | 실제 명세 확인 | 실제 명세 확인 | 미정 |
| End User 연결 | Connected ID | 인증정보/연결 방식 확인 | CODEF |
| 공동인증서 | 인증수단 등록·relay 문의 | API/Local/Server 방식 | 미정 |
| 테스트 환경 | 데모 제공 | 테스트베드 제공 | 동등 |
| SDK·개발 생태계 | 공식 SDK·가이드 | 개발가이드 제공 | CODEF 근소 우세 |
| 가격 공개성 | 법인카드 단가 비공개 | 기본료 공개 | Hyphen |
| 유사 SaaS 검증 | 그랜터 공개 적용 | ERP·경영관리 사례 안내 | CODEF |
| Provider 교체 용이성 | Adapter 적용 가능 | Adapter 적용 가능 | 동등 |
| 스크래핑 의존 | 있음/상품별 확인 | 공식적으로 명시 | 미정 |

매입이 공개 자료에 적혀 있다는 사실과 실제 TimeFit에 필요한 필드가 충분하다는 것은 다르다. 두 업체 모두 Sandbox 응답으로 승인번호, 취소구분, 원승인키, 매입일, 공급가액·부가세 여부를 확인해야 한다.

## 5. 인증·보안 비교

### CODEF 권장 흐름

```text
TimeFit 연결 요청
→ CODEF에 End User 인증수단 등록
→ Connected ID 발급
→ TimeFit은 Connected ID/reference만 저장
→ Connected ID로 카드 목록·내역 요청
```

장점:

- 고객별 연결을 불투명 ID로 관리하기 쉬움
- TimeFit 일반 DB에서 카드사 비밀번호와 인증서를 분리할 수 있음
- 재연결·기관 추가 구조가 명확함

확인 필요:

- 인증수단 원문이 TimeFit 서버를 통과하는지
- 인증서 relay 과정과 저장 주체
- Connected ID 삭제 시 인증수단 파기 보장
- CODEF 운영자/시스템의 접근통제와 보존기간

### Hyphen 권장 흐름

```text
TimeFit 연결 요청
→ Hyphen 인증 또는 스크래핑 세션
→ Hyphen connection reference 발급
→ TimeFit은 reference만 저장
→ 승인·매입 API 호출
```

확인 필요:

- 실제 상품이 불투명 connection reference를 제공하는지
- TimeFit이 카드사 ID/PW·인증서를 보관해야 하는지
- Server Scraping과 Local Scraping의 인증정보 책임 차이
- 재인증과 인증정보 파기 API 제공 여부

결론: CODEF는 공개 SDK에서 Connected ID 구조가 확인돼 현재로서는 보안 경계 설계가 더 명확하다. Hyphen도 같은 수준의 reference 방식을 제공한다면 차이는 줄어든다.

## 6. 수집 안정성 비교 포인트

두 Provider 모두 다음 시험을 동일하게 수행한다.

1. 보유카드 3장 발견
2. 최근 90일 승인 전체 조회
3. 전체취소 1건
4. 부분취소 1건
5. 승인 후 지연 매입 1건
6. 같은 기간 세 번 재조회
7. 페이지 중간 강제 실패 후 재개
8. 잘못된 인증정보와 계정 잠금 직전 처리
9. 카드사 점검·429·5xx 분류
10. 카드사 CSV와 일별 건수·순액 대사

평가 지표:

- 누락 건수
- 중복 건수
- 오합산 금액
- 원승인 연결 성공률
- 페이지 재개 성공률
- 인증 만료 판별 정확도
- 평균·p95 응답시간
- 카드사별 성공률
- 1,000건당 비용

## 7. 비용 비교

### 공개 가격

| 구분 | CODEF | Hyphen TR슬림 | Hyphen TR시그니처 |
|---|---:|---:|---:|
| 월 기본료 | 비공개 | 100,000원 | 300,000원부터 |
| 호출료 | 비공개 | 정상응답 건별 | 기본 건수 + 초과 협의 |
| 계약 | 정식 서비스 계약 확인 | 계약 없음 안내 | 계약 필요 |
| 테스트 | 데모 | 테스트베드 | 테스트베드 |
| 인증서 relay | 별도 문의 | 방식별 견적 확인 | 방식별 협의 |

부가세 포함 여부, 초기비, 최소 약정기간은 별도 확인한다.

### 예상 사용량 입력값

가정: 고객사당 카드 3장, 승인 6시간마다, 매입 하루 1회. 과금 단위가 카드별 호출일 때의 상한이며 실제 청구액은 아니다.

| 고객사 | 카드 | 승인 월 호출 | 매입 월 호출 | 정기 호출 합계 |
|---:|---:|---:|---:|---:|
| 1 | 3 | 360 | 90 | 450 |
| 10 | 30 | 3,600 | 900 | 4,500 |
| 100 | 300 | 36,000 | 9,000 | 45,000 |
| 1,000 | 3,000 | 360,000 | 90,000 | 450,000 |

추가 호출:

- 최초 90일 백필
- 페이지네이션
- 최근 7일 overlap 재대조
- 보유카드 discovery
- 재인증 검증
- 실패 재시도
- 월초 전월 매입 대사

### 손익 비교 공식

```text
월 Provider 총원가
= 월 기본료
+ billable request 수 × 요청 단가
+ Connected ID/카드/고객사 단가
+ relay·기술지원·전용환경 비용
+ 초기비 월환산액

고객사당 원가
= 월 Provider 총원가 ÷ 활성 고객사
```

가격 비교는 반드시 동일 조건으로 수행한다.

- 고객사 1·10·100·1,000곳
- 평균 카드 3장
- 승인 하루 4회
- 매입 하루 1회
- 최초 90일 백필
- 월 1회 전월 재대조
- SaaS 최종 고객 제공

## 10. 의사결정 시나리오

### CODEF 선택 조건

- Connected ID만으로 반복 조회 가능
- 인증서·비밀번호가 TimeFit을 거치지 않거나 즉시 폐기 가능
- 승인·부분취소·매입 필드가 충분함
- 멀티테넌트 SaaS 제공 권리가 계약에 포함됨
- 고객사 10·100곳 기준 원가가 TimeFit 플랜에 수용 가능

### Hyphen 선택 조건

- TR슬림 또는 시그니처에서 SaaS 제공 허용
- connection reference 방식 제공
- 부분취소 원승인키와 안정 event ID 제공
- 정상응답 건당 단가가 CODEF보다 유리
- 핵심 카드사의 2주 대사 품질이 CODEF와 동등

### 둘 다 사용하는 조건

- 카드사별 성공률 차이가 큼
- 대형 고객이 이중화를 요구
- 한 Provider의 장기 장애가 사업상 허용되지 않음

초기부터 자동 failover를 구현하지 않는다. 먼저 주 Provider와 CSV fallback을 운영하고, 고객·거래량이 커진 후 보조 Provider를 추가한다. 동일 거래가 두 Provider에서 들어올 경우 Provider event ID만으로 중복 제거할 수 없으므로 교차 Provider fingerprint와 수동 대사가 필요하다.

## 11. 업체에 보낼 최종 질문

1. 법인카드 보유·승인·전체취소·부분취소·매입 API 제공 여부
2. 원승인과 취소를 연결하는 필드
3. Provider event ID의 안정성과 unique 범위
4. 90일 이상 과거 조회와 pagination/cursor
5. 지원 카드사·법인/개인사업자·공용/개별카드
6. 공동인증서·ID/PW의 전달·보관·파기 주체
7. hosted 인증/relay/connection reference 제공 여부
8. 인증 만료·비밀번호 변경·추가인증 오류코드
9. TimeFit 고객에게 가공 내역·보고서를 제공할 권리
10. 고객사 1·10·100·1,000곳 구간 견적
11. 정상·무내역·오류·페이지의 과금 기준
12. 초기비·기본료·최소 약정·부가세
13. 호출 제한과 권장 동기화 주기
14. 카드사 변경 장애 SLA와 기술지원
15. 테스트베드에서 취소·부분취소·매입 fixture 제공 여부

## 12. 최종 권고

TimeFit이 그랜터 수준의 법인카드 연결 경험을 빠르게 구현하려면 CODEF를 상용 1순위로 두는 것이 타당하다. 이미 유사 제품에서 공개적으로 활용되고 있고 Connected ID 모델이 TimeFit의 보안 설계에 적합하기 때문이다.

그러나 비용·계약이 불리하거나 Sandbox 개통이 늦다면 Hyphen TR슬림으로 Pilot을 시작할 수 있다. Hyphen의 공개 월 기본료는 장점이지만 실제 총비용은 정상응답 단가와 과금 단위를 받아야 계산된다.
