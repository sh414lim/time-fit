# TimeFit 멀티테넌트 카드·지출관리 기획 검토 및 개발 예상 시나리오

## 1. 검토 결론

기획 방향은 조건부 승인한다. TimeFit은 금융 API를 외부에 판매하는 하이픈형 플랫폼이 아니라, 여러 회사가 카드 사용내역을 가져와 담당자·사유·영수증·계정과목·결산을 관리하는 그랜터형 SaaS로 정의한다. 데이터 수집은 `Partner First` 원칙에 따라 카드사 공식 API, 하이픈 등 전문 Provider, CSV·이메일 폴백 순으로 확보한다.

현재 TimeFit은 조직, 카드 연결, 카드 자산, 불변 거래 이벤트, 지출 원장, 영수증 매칭과 결산의 기본 모델을 보유하고 있어 전면 재개발할 필요는 없다. 그러나 외부 회사에 판매하기 전 멀티테넌트 격리, 세분화된 역할, 자격정보 보관, Provider 계약 확정과 실제 카드 대사를 출시 게이트로 추가해야 한다.

## 2. 승인·보완·제외 판정

### 2.1 승인

- 하나의 TimeFit에서 여러 회사를 지원한다.
- 회사마다 여러 카드사와 여러 법인카드를 연결한다.
- 카드 내역은 회사별 지출 원장으로 자동 반영한다.
- 카드에 직원·부서·매장을 연결한다.
- 직원이 지출 사유와 영수증을 제출한다.
- 가맹점 규칙으로 계정과목·사유·태그를 제안한다.
- 관리자는 정상 건이 아니라 예외 건을 우선 처리한다.
- 근태·급여·매출·지출을 회사별 손익으로 결합한다.

### 2.2 반드시 보완

| 영역 | 현재 | 필요 조치 |
| --- | --- | --- |
| 조직 격리 | 주요 테이블에 `organization_id` 존재 | API·Queue·Storage·Cache·Vault까지 교차 조직 테스트 |
| 역할 | owner/manager 중심 | 소유자, 비용관리자, 카드담당자, 직원, 조회자 분리 |
| Provider | mock/hyphen adapter 골격 | 실제 계약 API 명세와 테스트베드 연결 |
| 자격정보 | DB 암호문 저장 | Provider 직접 인증 또는 Vault reference 방식으로 전환 |
| 카드 식별 | provider ID fallback 존재 | 전체 카드번호 저장 가능성 제거, 토큰/HMAC 사용 |
| 수집 작업 | DB 기반 예약 실행 | 조직·Provider별 분산 잠금, 속도 제한, 비용 측정 |
| 연결 동의 | 버전 필드 중심 | 동의 전문, 범위, 철회, 보존기간 증적 |
| 운영 | 오류 분류 존재 | 운영자 콘솔, Provider 상태, 고객 알림과 사고 runbook |
| 보고서 | CSV·인쇄 PDF | 회계용 Excel과 확정본 버전 보존 보완 |

### 2.3 1차 출시 제외

- 자체 카드사 웹 스크래핑 엔진
- 개인 소비자 카드·자산관리
- 카드 결제 또는 송금 실행
- 전체 카드번호/CVC 저장
- 모든 카드사 동시 지원
- 외부 개발자용 금융 데이터 API 판매
- AI가 세무 적격성을 최종 확정하는 기능

## 3. 목표 사용자와 역할

### 회사 소유자

- 회사 생성과 대표 관리자 지정
- 금융정보 처리 동의
- Provider 및 법인카드 연결·해제
- 비용관리자 권한 부여
- 결산 확정·재오픈

### 비용관리자

- 연결된 카드와 거래 조회
- 카드 담당자·부서·매장 지정
- 계정과목·사유·태그 규칙 관리
- 영수증·미분류·중복 예외 검토
- 보고서 생성

### 카드 담당자

- 자신에게 지정된 카드와 거래 확인
- 거래 사유·프로젝트·영수증 제출
- 관리자 반려 건 수정

### 일반 직원

- 본인에게 요청된 지출 증빙만 확인·제출
- 다른 직원 또는 회사의 금융정보 조회 불가

### 조회 전용 사용자

- 승인된 범위의 보고서와 확정 원장 조회
- 카드 연결·지출 수정·결산 확정 불가

### TimeFit 운영자

- 조직 금융 데이터 원문은 기본적으로 조회 불가
- Provider 연결 상태와 익명화된 장애 지표만 조회
- 고객 승인과 break-glass 절차가 있어야 제한적 지원 가능

## 4. 핵심 도메인 구조

```text
Organization
 ├─ Membership / Finance Role
 ├─ Provider Connection
 │   ├─ Consent
 │   ├─ Credential Reference
 │   ├─ Card Asset
 │   └─ Sync Run / Cursor
 ├─ Immutable Card Event
 │   └─ Transaction Group
 ├─ Receipt / Evidence
 │   └─ Match Candidate
 ├─ Expense Ledger
 │   ├─ Category / Tag / Project
 │   └─ Audit Log
 └─ Closeout / Report Version
```

모든 하위 객체는 `organization_id`를 직접 보유한다. 상위 객체 조인만으로 조직을 추론하지 않는다. 객체를 생성·갱신할 때 요청 조직과 참조 대상의 조직이 동일한지 DB 제약 또는 RPC에서 재검증한다.

## 5. 사용자 예상 시나리오

### S01. 신규 회사 온보딩

사전조건: 회사 소유자가 TimeFit 계정을 생성했다.

1. 회사명, 사업자번호와 담당자 정보를 입력한다.
2. TimeFit은 독립된 조직 ID를 생성한다.
3. 소유자 membership과 기본 비용관리 역할을 생성한다.
4. 카드·영수증 데이터 처리 범위와 보존기간을 안내한다.
5. 소유자가 동의하면 동의 전문 hash와 시각을 저장한다.
6. 회사별 카드 연결 화면을 연다.

완료 기준:

- 다른 회사의 직원·카드·거래가 한 건도 노출되지 않는다.
- 동의를 하지 않아도 근태 기능은 사용할 수 있지만 카드 연결은 시작할 수 없다.
- 동일 사용자가 여러 회사에 속하면 현재 회사가 명확하게 표시된다.

### S02. Provider를 통한 첫 카드 연결

1. 소유자가 `법인카드 연결`을 누른다.
2. TimeFit이 지원 Provider와 카드사 목록을 표시한다.
3. 소유자가 카드사와 사업자 유형을 선택한다.
4. 인증정보는 TimeFit 일반 DB를 통하지 않고 Provider 또는 Credential Broker로 전달한다.
5. 인증 성공 후 보유카드 목록을 조회한다.
6. 화면에는 카드사, 카드명과 마지막 네 자리만 표시한다.
7. 소유자가 수집할 카드를 선택한다.
8. 카드 자산을 조직에 연결하고 90일 백필을 예약한다.

완료 기준:

- 전체 카드번호와 CVC가 브라우저 로그, 서버 로그, DB에 존재하지 않는다.
- 연결 요청자와 동의 버전이 감사 로그에 남는다.
- 같은 Provider 연결을 중복 생성해도 하나의 활성 연결만 존재한다.

### S03. 여러 카드사와 여러 카드 연결

1. 회사가 카드사 A에서 카드 3장, 카드사 B에서 카드 2장을 연결한다.
2. 동일 카드가 재조회되면 기존 자산을 갱신한다.
3. 신규 발급 카드는 `발견됨` 상태로 표시하고 자동 수집 여부를 묻는다.
4. 해지 카드는 과거 거래를 보존하면서 `비활성`으로 전환한다.

완료 기준:

- Provider별 식별자가 충돌해도 회사·Provider·기관 범위에서 정확히 구분된다.
- 카드 재발급은 새 자산으로 처리하되 이전 카드와의 관계를 기록할 수 있다.

### S04. 카드 담당자 지정

1. 비용관리자가 카드에 직원, 부서 또는 매장을 지정한다.
2. 담당자는 해당 카드 신규 거래의 증빙 요청을 받는다.
3. 담당자 변경 시 변경 이후 거래부터 새 담당자를 기본 지정한다.
4. 과거 거래 담당자는 명시적 일괄 변경을 하지 않는 한 유지한다.

완료 기준:

- 직원은 본인 담당 거래만 조회한다.
- 담당자 변경 이력과 적용 시점이 남는다.

### S05. 최초 90일 내역 수집

1. Worker가 카드별·기간별 작업을 생성한다.
2. Provider 페이지를 순차 조회한다.
3. 응답 원본을 보안 정책에 따라 저장 또는 즉시 최소화한다.
4. 승인·취소·부분취소·매입을 표준 이벤트로 변환한다.
5. 멱등 키로 중복 이벤트를 제거한다.
6. 거래 그룹과 지출 초안을 생성한다.
7. 진행률을 연결 화면에 표시한다.

완료 기준:

- 작업 재실행 후 거래 수와 합계가 동일하다.
- 일부 페이지 실패 시 성공한 범위를 잃지 않고 실패 지점부터 재개한다.
- 완료되기 전까지 데이터 신선도와 `수집 중` 상태가 표시된다.

### S06. 정기 증분 수집

1. Scheduler가 마지막 성공 커서와 시각을 읽는다.
2. 지연 취소·매입을 위해 이전 기간 일부를 겹쳐 조회한다.
3. 신규 이벤트만 저장한다.
4. 성공한 카드의 커서만 전진시킨다.
5. 다음 동기화 예정 시각을 표시한다.

완료 기준:

- 중복 합산 0건
- 실패 카드 때문에 다른 카드의 수집이 중단되지 않음
- 조직별·Provider별 호출량과 비용 추적 가능

### S07. 승인 후 부분취소

1. 100,000원 승인이 수집된다.
2. 지출 원장에 잠정 100,000원이 표시된다.
3. 이후 20,000원 부분취소가 수집된다.
4. 동일 거래 그룹의 취소액이 20,000원, 순액이 80,000원으로 변경된다.
5. 기존 영수증은 유지하되 금액 차이 예외를 생성한다.

완료 기준:

- 승인과 취소를 두 지출로 합산하지 않는다.
- 확정 결산 이후 발생한 취소는 결산을 조용히 수정하지 않는다.

### S08. 직원의 사유·영수증 제출

1. 신규 거래가 담당 직원에게 표시된다.
2. 직원이 사유, 프로젝트, 태그와 영수증을 제출한다.
3. OCR이 날짜·금액·가맹점·승인번호를 추출한다.
4. 카드 거래 후보 점수를 계산한다.
5. 고신뢰 매칭은 정책에 따라 추천 또는 자동 연결한다.

완료 기준:

- 직원은 금액과 카드 원본을 수정할 수 없다.
- 영수증 원본과 추출값을 비교할 수 있다.
- 같은 영수증 중복 업로드가 차단된다.

### S09. 계정과목 자동화

1. 관리자가 특정 가맹점의 거래를 `소모품비`로 확정한다.
2. `이 사업자번호는 소모품비로 기억`을 선택한다.
3. 이후 같은 사업자번호 거래에 규칙이 적용된다.
4. 낮은 신뢰도 또는 충돌 규칙은 관리자 검토 대상으로 남는다.

완료 기준:

- 규칙은 회사 내부에서만 적용된다.
- 사업자번호 규칙이 상호명 규칙보다 우선한다.
- 규칙 생성·수정·삭제 이력이 남는다.

### S10. Provider 인증 만료

1. 정기 수집에서 인증 오류가 발생한다.
2. 연결을 `reauth_required`로 전환한다.
3. 자동 재시도를 중단한다.
4. 소유자에게 재인증 요청을 보낸다.
5. 새 인증정보로 보유카드 조회에 성공하면 자격정보를 교체한다.
6. 누락 기간을 자동 백필한다.

완료 기준:

- 인증 실패를 반복 호출해 계정이 잠기지 않는다.
- 새 인증 검증 실패 시 기존 자격정보를 덮어쓰지 않는다.
- 자격정보 값은 감사 로그에 남지 않는다.

### S11. Provider 장애 또는 호출 제한

1. Provider가 429 또는 5xx를 반환한다.
2. 오류 종류에 맞는 backoff를 적용한다.
3. 마지막 정상 데이터를 유지한다.
4. 화면에 최근 성공 시각과 다음 재시도 시각을 표시한다.
5. 장애가 길어지면 CSV 가져오기를 제안한다.

완료 기준:

- 화면에 0원으로 덮어쓰지 않는다.
- 회사별 원장과 확정 결산은 유지된다.
- 장애 복구 후 누락 기간을 중복 없이 수집한다.

### S12. CSV 폴백

1. 관리자가 카드사 CSV를 업로드한다.
2. TimeFit이 카드사·컬럼·날짜·금액을 미리보기로 보여준다.
3. 사용자가 카드와 매핑한다.
4. 파일 hash와 행 지문으로 중복을 검사한다.
5. 성공·중복·오류 행을 분리해 결과를 제공한다.

완료 기준:

- 같은 파일을 세 번 올려도 합계가 바뀌지 않는다.
- Provider 데이터와 동일 거래가 중복 지출로 생성되지 않는다.
- 오류 행을 수정해 재업로드할 수 있다.

### S13. 회사 전환과 교차 조직 공격

1. 한 사용자가 회사 A와 B의 관리자다.
2. A 화면에서 B의 `organizationId` 또는 객체 ID를 임의 요청한다.
3. API와 DB가 요청을 거부한다.
4. Storage URL, 캐시와 작업 상태도 B 데이터를 반환하지 않는다.

완료 기준:

- API, DB, Storage, Queue, Cache 전 계층에서 교차 조회 0건
- 거부 이벤트가 보안 로그에 남음

### S14. 결산 확정 후 변경

1. 관리자가 월 결산 스냅샷을 저장하고 확정한다.
2. 이후 늦은 매입 또는 취소가 수집된다.
3. 확정 버전은 변경하지 않는다.
4. 다음 기간 조정 또는 사유를 포함한 재오픈을 요청한다.

완료 기준:

- 화면, CSV와 PDF의 확정 합계가 동일하다.
- 재오픈 주체·사유·시각이 기록된다.

### S15. 카드 연결 해제와 회사 탈퇴

1. 소유자가 카드 연결을 해제한다.
2. 신규 수집을 중단하고 예약 작업을 취소한다.
3. Provider 토큰과 자격정보를 폐기한다.
4. 세무·감사 보존 대상 원장과 확정본은 정책에 따라 유지한다.
5. 회사 탈퇴 시 보존 대상과 즉시 삭제 대상을 안내한다.

완료 기준:

- 해제 후 Provider 호출 0건
- 폐기 증적과 잔존 데이터 목록 확인 가능

## 6. 시스템 처리 예상 시나리오

### 연결 성공

```text
Web -> Connection API: 조직·Provider·동의
Connection API -> Authorization: owner 검증
Connection API -> Provider: 인증 시작
Provider -> Connection API: credential reference
Connection API -> Provider: 보유카드 조회
Connection API -> DB: 마스킹 카드 저장
Connection API -> Queue: 90일 backfill
Worker -> Provider: 승인·취소·매입 조회
Worker -> Event Store: 멱등 이벤트 저장
Event Store -> Ledger: 거래 그룹·지출 생성
Web <- Connection API: 진행률·최근 성공
```

### 조직 격리 실패 차단

```text
Request(org A, object of org B)
 -> membership 검증
 -> object.organization_id 검증
 -> 불일치 403
 -> security audit 기록
 -> 데이터 body 반환 없음
```

### Provider 장애 복구

```text
Worker -> Provider: fetch
Provider -> Worker: 429/5xx/timeout
Worker -> Error Classifier
 -> retryable: next_sync_at 계산
 -> authentication: reauth_required
 -> schema_changed: connector kill switch
UI <- 상태·최근 성공·다음 조치
```

## 7. 현재 코드 재사용 판단

### 그대로 발전 가능

- `timefit_user_organizations`와 membership
- 카드 connection·asset·sync run·cursor
- 카드 거래 event·group
- 지출·source·match·audit 구조
- 영수증 OCR·중복 방지·검토 화면
- 가맹점 분류 규칙
- 결산·재오픈·보고서
- 장애 분류와 재인증 상태

### 리팩터링 필요

- `ownerOnly` 중심 권한을 finance permission으로 분리
- Provider 자격정보를 DB ciphertext에서 Vault reference로 전환
- 전체 카드번호가 provider ID fallback으로 저장될 가능성 제거
- Vercel 함수에서 장기 수집 Worker 분리
- sync worker에 조직·Provider별 concurrency lock 추가
- Provider API 응답 schema version과 raw payload 정책 추가
- 회사 전환 시 캐시 key와 화면 상태 초기화 검증

### 신규 개발 필요

- 회사 대표·사업자 검증과 금융 동의 증적
- Provider 계약 기반 실제 연결 화면
- 카드 담당자 적용 시작일
- 직원 지출 요청함
- 조직별 finance role/permission
- 연결·수집 운영자 콘솔
- CSV 매핑 미리보기와 오류 리포트
- Excel 확정 보고서
- tenant isolation 자동 E2E

## 12. 최종 권고

첫 개발은 카드사 연결 화면이 아니라 멀티테넌트 보안 기반이어야 한다. 현재 화면에 실제 Provider 입력란을 먼저 붙이면 기능은 빨리 보이지만 회사 간 데이터 격리와 자격정보 책임을 나중에 수정하기 어렵다.

권장 착수 순서는 다음으로 확정한다.

```text
조직 격리·권한·카드번호 비저장
→ Provider 계약 인터페이스
→ 실제 Provider 1개 연결
→ 90일 CSV 대사
→ 직원 사유·영수증 흐름
→ 자동화·예외 업무
→ 결산·운영 검증
```
