# 운영 피드백 UX 개선안

상태: 2026-09-17 실제 애플리케이션 코드 반영 완료. 정정 이력용 DB 마이그레이션 작성·격리 DB 검증 완료. 운영 배포 및 운영 DB 적용은 아직 하지 않았다.

작성일: 2026-09-17. 데이터는 해당 일 조회 스냅샷이며 실시간 수치가 아니다.

## 1. 목적과 범위

사장님이 홈에서 확인할 기록을 발견하고, 해당 기록으로 이동해 처리하며, 지난주 매출 변화를 이해하는 흐름을 만든다.

첫 구현 범위:

- 홈의 확인할 일 통합: 근태 기록, 휴가 승인, 급여 초안 확인, 미검토 카드 내역.
- 홈의 지난주 매장 요약: 완료 주문 매출, 완료 주문 수, 주문당 평균 금액, 대표 메뉴 변화.
- 매출 분석의 주간 비교와 메뉴 변화 상세.
- 확인 항목에서 기존 업무 화면의 대상 기간·필터·기록까지 이어지는 이동.

적정 인원 추천, 인건비 절감액, 메뉴 이익 순위, 수요 예측, 실시간 매출 경보는 이번 범위에 포함하지 않는다.

## 2. 현재 화면의 문제와 변경

현재 홈은 요약 숫자, 실시간 출퇴근, 휴가 승인, 미출근 알림, 주간 스케줄이 순서대로 표시된다. 확인할 업무가 여러 영역에 흩어지고 매출 해석은 없다. 현재 ‘확인 필요’ 숫자는 시작 시간이 지나지 않은 오늘 근무자도 포함할 수 있으므로 그대로 재사용하지 않는다.

현재 매출 분석은 누적 매출·주문·취소와 최근 주문 목록 중심이다. 기간·비교 기준을 먼저 보여주고 변화의 근거를 설명한다.

현재 지출·증빙은 지출 장부, 알림 설정, 카드, 예외 처리, 증빙 검토, 결산 등이 한 페이지에 길게 이어진다. 홈에서 진입할 때 페이지 최상단만 열지 말고 대상 목록까지 이동한다.

### 홈 구조

1. 사업장·조회 날짜.
2. 확인할 일: 유형별 최대 3개 우선 표시, 나머지 펼치기.
3. 지난주 매장 요약: 월~일 완료 주, 전주 월~일 대비.
4. 오늘 출퇴근 현황.
5. 이번 주 스케줄.

기존 출근·근무 중 요약 숫자는 출퇴근 영역의 제목 옆으로 모아 상단의 큰 카드 중복을 줄인다. 예상 인건비는 급여 관리에 배치하고 계산 범위를 명시한다.

새로운 ‘AI 피드백’ 메뉴는 만들지 않는다. 고객 리뷰와 운영 분석은 의미가 다르므로 리뷰·컴플레인 화면에 넣지 않는다.

### 내비게이션

데스크톱 시안은 기존 3개 메뉴 그룹을 사이드바의 구분 제목으로 보여주고 홈을 항상 노출한다. 그룹을 바꿀 때 홈이 숨겨지는 문제를 줄인다. 메뉴 이름과 권한은 유지한다.

모바일은 기존 하단 홈·출퇴근·스케줄·더보기 구조를 유지한다. 홈에서 매출 요약을 누르면 매출 분석으로 이동하고 홈으로 돌아갈 수 있다.

## 3. 확인할 일: 표시와 행동

| 유형 | 데이터 조건 | 노출 문구 | 이동 대상 | 해결 조건 |
|---|---|---|---|---|
| 퇴근 미기록 | 이전 날짜 출근 있음, 퇴근 없음. 야간 근무는 종료 예정 이후 유예 적용 | 퇴근 기록이 없는 이전 근무 N건 | 출퇴근의 기간 전체 확인 목록, 해당 유형 필터 | 실제 퇴근 기록 보완 |
| 예정 근무의 기록 없음 | 승인된 근무·휴무 아님·예정 종료 지남·출퇴근 행 없음 | 예정 근무의 출퇴근 기록을 확인해주세요 | 대상 일정과 출퇴근 기록 대조 | 근무 취소/일정 정정/실제 기록 보완 |
| 승인 일정 불일치 | 출퇴근 존재, 승인된 근무 없음 또는 휴무 | 실제 근무와 승인 일정을 대조해주세요 | 해당 직원·날짜의 일정과 출퇴근 | 승인 일정 또는 기록 정정 |
| 휴가 승인 | 실제 pending 요청 | 승인할 휴가 N건 | 기존 요청 검토 화면 | 승인/반려 등 원본 상태 변경 |
| 급여 초안 | 저장 시각과 대상 월 표시. 영향 있는 원본 변경 확인 시 갱신 필요 표시 | 9월 급여 초안 · 마지막 저장 9/12 | 해당 월 급여 관리 | 최신 근거로 초안 재계산·저장 |
| 미검토 카드 | 거래 그룹의 미검토 상태, 선택 범위 내 | 미검토 카드 내역 N건 | 지출·증빙의 미검토 거래 목록 | 실제 검토 상태 변경 |

### 처리 원칙

- 결근·무단 근무로 단정하지 않는다. 확인 사실과 필요한 행동만 표현한다.
- 퇴근 미기록과 승인 일정 불일치는 같은 근무에 동시에 발생할 수 있다. 유형별 건수를 단순 합산하지 않는다.
- 홈은 ‘3가지’처럼 유형 수를 표시한다. 전체 기록 수가 필요하면 staff_id + work_date 등 업무별 원본 키로 중복 제거한다.
- 읽음/확인 완료를 해결로 취급하지 않는다. 실제 원본 상태를 다시 조회해 목록에서 제거한다.
- 운영상 영향·기한 기준으로 정렬한다. 시안에서는 과거 근태, 급여 초안, 카드 검토 순서다.
- 이전 날짜 기록도 무조건 오류는 아니다. 자정 넘는 근무와 사업장 설정을 적용한다.
- 급여 초안이 오래됐다는 사실만으로 계산 오류라고 표시하지 않는다. 초안 이후 해당 월에 영향을 주는 근태·일정·계약·설정·조정 변경을 확인해야 ‘재계산 필요’로 확정한다.
- 테스트 표시 지출은 검토 후보로만 표시한다. 문자열만으로 삭제하거나 비용에서 제외하지 않는다.

## 4. 주간 매출 및 메뉴

### 기간

- KST 기준 최근 완료된 월~일을 기본값으로 한다.
- 홈과 상세 분석은 동일한 from/to/comparisonFrom/comparisonTo를 공유한다.
- 진행 중인 주와 전체 전주를 비교하지 않는다. 추후 이번 주 보기를 추가하면 같은 경과 요일까지 비교한다.
- 출퇴근과 주간 리포트가 서로 다른 주 시작 요일을 사용 중이다. 리포트는 월~일로 명시하고 기존 스케줄을 암묵적으로 변경하지 않는다.

### 계산

- 현재 확인 데이터의 state=COMPLETED를 완료 주문으로 사용한다. 미확인 상태를 취소가 아니라는 이유로 완료로 포함하지 않는다.
- 주문당 평균 금액 = 완료 주문 total_amount 합 / 완료 주문 수.
- 변동률 = (현재 - 비교) / 비교. 비교값 0이면 백분율 대신 ‘비교 기준 없음’과 절대 차이를 표시한다.
- 방문객 수·객단가라고 표현하지 않는다. 인원 정보가 없으므로 주문당 금액으로 명명한다.
- 메뉴는 완료 주문의 lineItems에서 수량 집계. 메뉴 코드가 존재하면 코드 우선, 없으면 이름 기준 집계와 이름 변경 한계를 명시한다.
- 무료 메뉴를 유료 판매 순위에서 제외한다. 메뉴 매출을 추가한다면 주문·항목 할인과 옵션 반영 기준을 먼저 정한다. 이번 화면은 수량만 사용한다.
- 메뉴 수량 증가는 재고 확인의 근거로만 사용하고 발주량·수익성·원인을 추정하지 않는다.

### 원본 대조 기준

운영 데이터의 완료 주문 합계·주문 수·주문당 금액·메뉴 수량을 새 집계 함수와 대조해 일치를 확인했다. 공개 문서에는 실제 사업장의 금액·근태 건수·메뉴별 수량을 포함하지 않는다.

원본이 수정되면 확인 항목 수가 달라지므로 조회 스냅샷을 제품에 하드코딩하지 않는다. 근태 확인 항목은 검토 대상이며 결근 수가 아니다.

## 5. 화면 동작 계약

| 시작 | 전달할 상태 | 도착 |
|---|---|---|
| 홈 → 퇴근 미기록 | 기간, issueType=missing_checkout, 목록에서 선택한 staffId/workDate | 출퇴근 확인 목록 → 기록 상세 |
| 홈 → 급여 초안 | settlementMonth | 해당 월 초안과 반영 기준 |
| 홈 → 카드 검토 | reconciliationStatus=unreviewed, 수록 기간 | 미검토 카드 거래 목록 |
| 홈 → 매출 상세 | from/to 및 comparisonFrom/comparisonTo | 주간 요약 |
| 홈 → 메뉴 변화 | 같은 기간, tab=menu | 메뉴 변화 |
| 상세 → 뒤로 | 이전 홈 또는 목록의 필터·스크롤 | 이전 작업 위치 |

현재 setActive(id)만으로는 기간·필터 전달이 안 된다. navigation context 또는 URL 상태를 추가하고, 대상 화면에서 전달값을 초기화에 사용한다. 다른 직원/사업장으로 전환되면 이전 상태와 캐시를 분리한다.

## 6. 상태·권한·신뢰성

### 데이터 상태

- 로딩: 영역 단위 스켈레톤. 다른 홈 기능을 가리지 않는다.
- 데이터 없음: 연결/수록 상태를 설명. 수집 실패를 매출 0원으로 표시하지 않는다.
- 비교 불가: 확보된 기간은 표시하되 증감·해석은 숨긴다.
- 수집 지연: 마지막 성공 수집 시각과 대상 기간을 표시하고 결과를 마지막 수집분으로 명명한다.
- 확인할 항목 없음: 짧은 완료 상태 한 줄. 빈 카드 공간을 크게 남기지 않는다.
- 오류: 해당 영역의 재시도. 기존 데이터가 있으면 마지막 조회분이라고 표시해 유지한다.

### 권한

- 최고관리자: 사업장 범위의 전체 허용 기능.
- 관리 계정: 현재 permissions/scopes의 직원·업무 범위로 서버에서 집계한다.
- 홈 접근 권한이 매출·지출·급여 조회 권한을 의미하지 않는다.
- 현재 위임 관리 계정에는 매출·지출 메뉴 권한 매핑이 없다. 새 요약을 홈에 추가하면서 재무 정보를 노출하지 않는다. 필요하면 별도 권한 설계 후 적용한다.
- 상세 화면 권한과 홈 요약의 권한을 같게 한다. 건수·금액만으로도 권한 밖 정보를 노출하지 않도록 한다.

### 수집 및 집계의 구현 전제

- 현재 자동 매출 수집 설정은 한국시간 22시 1회다. 실시간 표기를 사용하지 않는다.
- 성공 시각만으로 당일 전체 데이터가 완결됐다고 판단하지 않는다. 마감 시간·후속 취소 반영·API 페이지 수집을 확인한다.
- 현재 sync-sales는 요청당 기본 첫 페이지 최대 500건을 처리한다. 조회 구간이 500건을 넘는 경우 전체 페이지 수집을 보장한 뒤 비교 리포트를 확정한다.
- 같은 merchant_id가 여러 조직에 연결되어 있다. 주문의 organization_id와 조직별 캐시 집계 범위를 검증하고 다른 조직 이력을 섞지 않는다.
- 0원인 날과 수집되지 않은 날을 구분할 근거가 부족하면 임의로 0을 채우지 않는다.
- 카드 승인 이벤트와 거래 그룹은 동일 거래의 다른 표현이다. 카드 검토 건수/금액은 거래 그룹 기준으로 집계한다.
- 카드 파일 수록 범위와 마지막 가져온 시각을 표시한다. 수록된 거래가 전체 지출이라고 주장하지 않는다.
- 카카오·푸시 자동 발송은 이번 범위 밖이다. 현재 관련 코드는 설정 대기 상태를 저장한다.

## 7. 시각 디자인

- 기존 TimeFit의 파란색, 중립 배경, 둥근 사각형 언어 유지.
- 모든 정보를 개별 카드로 만들지 않는다. 업무는 한 패널 안의 행, 매출 수치는 한 패널 안의 3열로 묶는다.
- 제목 → 사실 → 근거 기간 → 행동의 순서. ‘AI 점수’나 근거 없는 위험 배지 제외.
- 과거 누락 같은 확인 항목에만 주황색. 매출 감소는 자동으로 위험 판정하지 않고 중립색과 감소 기호로 표현한다.
- 주간 요약에 일별 비교 차트를 중복 배치하지 않는다. 홈은 결론, 상세는 근거를 보여준다.
- 모바일은 한 열. 큰 금액을 먼저 보여주고 주문 수·주문당 금액은 아래 두 열에 배치한다.
- 날짜·필터·주요 행동을 모바일에서도 숨기지 않는다. 키보드와 터치로 동작한다.

## 8. 구현 수용 기준

1. 두 완료 주의 조회 결과가 같은 기간 원본 집계와 일치한다.
2. 홈 요약에서 상세로 이동해도 기간과 금액이 바뀌지 않는다.
3. 퇴근 미기록 행을 누르면 해당 날짜·직원 기록을 찾기 위한 추가 검색이 필요 없다.
4. 원본을 보완하면 재조회 후 확인 목록에서 제거된다. 알림 읽음만으로는 사라지지 않는다.
5. 미래 일정·진행 중인 정상 근무를 과거 누락 목록에 포함하지 않는다.
6. 휴무·반려·미승인 일정 처리와 여러 확인 유형의 중복 제거를 검증한다.
7. 조회 권한이 없는 급여·매출·지출은 요약 건수와 금액도 표시하지 않는다.
8. 실패·비교기간 미확보·전주 0원에서 허위 0원·무한대 증감·과도한 해석이 나오지 않는다.
9. 수집 시각과 화면을 연 시각을 구분한다.
10. 320px 모바일에서도 금액·기간·버튼이 겹치지 않고 같은 작업을 수행할 수 있다.

## 9. 검토용 시안의 범위

대화에 삽입한 시안은 홈, 주간 매출, 메뉴 변화, 근태 확인, 급여 준비, 지출 검토의 화면 이동을 보여준다. 운영 데이터 수정·발송·급여 저장은 하지 않는다. 개인별 근태 상세와 기존 업무 기능 전체는 시안에서 생략했다.

디자인 조정으로 ‘확인할 일 먼저 / 지난주 매출 먼저’와 정보 간격을 비교할 수 있다. 기본안은 확인할 일 먼저, 여유 있는 간격이다.

## 10. 반복 검토 결과 — 2026-09-17

검토 대상은 대화 내 시안이다. 실제 어드민 코드·운영 DB·알림 발송은 변경하지 않았다. 최초 시안은 보존하고 개선본을 `timefit-operations-review.html`로 작성했다.

### 1차: 사용자 여정과 막힌 화면

발견:

- 근태 유형 두 개는 설명문만 있고 실제 목록이 없었다.
- 카드 검토 버튼도 합계 설명에서 끝났다.
- 근태 필터를 바꾸고 홈의 퇴근 미기록으로 재진입하면 다른 유형이 남았다.
- 급여 → 근태 이후 돌아가기의 출발 화면이 보존되지 않았다.

개선:

- 실제 조회 자료를 익명화해 퇴근 미기록 3건, 출퇴근 기록 없는 일정 9건, 일정 확인 31건의 목록과 상세 연결을 추가했다.
- 카드 목록을 가맹점·날짜·금액으로 조회하고 상세로 들어갈 수 있게 했다.
- 링크 목적에 맞는 기간·유형으로 진입하고, 뒤로 가면 필터·펼친 목록 길이를 복구한다.
- 상세는 직원명 대신 일관된 익명 번호와 부서로 표시한다. 원본 식별자는 시안에 포함하지 않는다.

### 2차: 모바일과 입력 흐름

발견:

- 긴 홈 문구가 주요 내용을 아래로 밀었다.
- 모바일에서 사이드바가 없어지면 다른 업무로 이동하기 어려웠다.
- 화면 이동 후 이전 스크롤이 남아 새 제목과 기간을 놓칠 수 있었다.
- 요일 차트가 좁은 화면에서 두 줄로 갈라져 주간 흐름을 읽기 어려웠다.
- 샌드박스 내 form 제출은 시안의 변경 내용 확인 동작을 실행하지 못했다.

개선:

- 홈 문구를 짧게 줄이고, 주요 확인 유형 3개와 추가 근태 유형 펼치기를 분리했다.
- 시안에 포함된 화면은 모바일 메뉴로 이동 가능하게 했다. 실제 제품 적용 시 기존 하단 내비게이션과 중복되지 않게 통합한다.
- 상세 진입 시 상단과 초점을 이동하고, 뒤로 가기에서는 이전 위치를 복구한다.
- 요일 차트를 가로 막대 7행으로 바꾸고 두 주 금액을 직접 표시했다. 눌러 증감 금액을 확인할 수 있다.
- 날짜·시각·사유 입력 → 변경 내용 확인 → 시안에서 적용 → 확인 건수 감소의 국소 상태 흐름을 추가했다.
- 확인 버튼을 로컬 클릭 동작으로 바꾸고, 누락 값·출근 이전 시각·짧은 사유·조회 기준일 이후 입력을 검증한다.
- ‘시안에만 적용’ 표시와 초기화를 제공한다. 수정 내용은 브라우저 메모리에만 존재하고 새로고침 시 초기화된다.

### 3차: 데이터 신뢰성과 권한

발견:

- 비교 기간 미확보 예시에서도 메뉴 표의 전주 수량과 증감이 남았다.
- 근태 조회 담당자에게도 수정 입력을 보일 수 있었다.
- 알림의 유형 수와 원본 기록 건수를 혼동할 여지가 있었다.

개선:

- 비교 기간이 없을 때 전주 열·증감·요일 비교·해석을 함께 숨기고 확보된 실적만 표시한다.
- 권한별 시안에서 근태 조회 담당자에게 매출·급여·지출 메뉴와 요약을 표시하지 않고 기록 수정 입력도 숨긴다.
- 배지는 ‘3가지 우선 표시’처럼 유형 수로 표현한다. 중복될 수 있는 근무 건수를 합산하지 않는다.
- Tweak에서 최고관리자/근태 조회 담당자, 정상/수집 지연/비교 기간 미확보 상태를 비교할 수 있다.
- 이 시안의 숨김은 UI 검토용이다. 실제 권한 보장은 서버 조회 범위에서 적용해야 한다.

### 브라우저에서 확인한 항목

- 데스크톱 1024px 배치와 모바일 약 320px 콘텐츠 폭의 홈·메뉴 비교 표시.
- 모바일 해당 화면에서 가로 넘침 없음.
- 홈 퇴근 미기록 버튼 재진입 시 올바른 유형 선택.
- 수정 입력 누락 및 출근 이전 시각 차단.
- 수정 내용 확인 뒤 로컬 적용 시 퇴근 미기록 감소, 홈과 목록 동시 갱신.
- 급여 → 근태 → 뒤로 이동 시 급여 화면 복귀.
- 카드 목록 전체 표시, 상세 복귀 시 목록 유지.
- 비교 불가 상태에서는 메뉴 표에 메뉴명과 지난주 수량만 표시.
- 근태 조회 담당자 화면에 재무 요약과 수정 입력 없음.
- 수집 지연 상태에서 마지막 확보 자료라는 안내 표시.

미검증 범위: 운영 API 권한, 실제 기록 저장, 외부 알림, 최신 데이터 재집계, 기존 관리자 UI와 병합 후 회귀 테스트. 이번 결과를 운영 기능 완료로 간주하지 않는다.
