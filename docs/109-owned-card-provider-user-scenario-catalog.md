# TimeFit 자체 법인카드 Provider 사용자 시나리오

## 1. 문서 관계

이 문서는 `108-timefit-owned-corporate-card-provider-master-prd.md`의 사용자 시나리오 상세 문서다. 제품·기술·보안 기준은 전체 기획 정의서를 따르고, 이 문서는 실제 사용자가 어떤 화면에서 어떤 행동을 하며 시스템이 어떻게 반응해야 하는지를 정의한다.

## 2. 주요 사용자

| 사용자 | 목적 | 주요 기능 |
| --- | --- | --- |
| 회사 소유자 | 회사 카드 연결과 금융정보 통제 | 동의·인증·재인증·해제·결산 |
| 비용관리자 | 카드·거래·증빙 관리 | 카드 선택·담당자 지정·대사·예외 검토 |
| 카드 담당 직원 | 사용한 카드 증빙 제출 | 사유·프로젝트·태그·영수증 |
| 조회자 | 재무 현황 확인 | 확정 원장·보고서 조회 |
| TimeFit 운영자 | Connector 안정성 운영 | 장애·작업·버전·kill switch |

## 3. 전체 사용자 여정

```text
[회사 소유자]
카드 연결 동의·인증
        ↓
[비용관리자]
보유카드 선택·담당자 지정
        ↓
[TimeFit]
90일 수집·CSV 대사·자동 동기화
        ↓
[카드 담당 직원]
사유·영수증 제출
        ↓
[비용관리자]
예외 검토·확정
        ↓
[회사 소유자]
월 결산·보고서
```

## 4. 회사 소유자 시나리오

### O01. 첫 카드사 연결

목표: 회사가 처음으로 법인카드를 TimeFit에 연결한다.

사전조건:

- 회사 조직이 생성되어 있다.
- 사용자가 회사 소유자다.
- 사업자번호가 등록되어 있다.

진행:

1. 소유자가 `설정 > 금융 연동`을 연다.
2. `카드사 연결`을 누른다.
3. 지원 카드사와 인증 방식을 확인한다.
4. 카드정보 수집·이용·보관·해제 정책을 확인한다.
5. 필수 동의를 완료한다.
6. 법인사업자와 카드사를 선택한다.
7. 공동인증서 또는 기업 ID 인증을 선택한다.
8. 인증을 완료한다.
9. 추가 인증이 필요하면 TimeFit modal에서 처리한다.
10. 인증 성공 후 보유카드 화면으로 이동한다.

시스템 처리:

- 동의 전문 hash·version·동의자·시각 저장
- 인증정보를 Vault에 보관하거나 1회 사용 후 폐기
- connection 상태 변경
- 카드사 Connector session 생성
- 보유카드 discovery job 생성

성공 결과:

- 사용자는 TimeFit을 벗어나지 않고 인증을 완료한다.
- 카드사·상품명·last4만 포함된 보유카드 목록이 표시된다.
- 전체 카드번호·CVC·인증 비밀번호가 DB와 로그에 없다.

### O02. 공동인증서 만료

1. 사용자가 만료된 인증서를 선택한다.
2. TimeFit이 카드사 로그인 전에 만료를 감지한다.
3. 만료일과 새 인증서가 필요하다는 안내를 표시한다.
4. 연결은 생성하지 않거나 기존 연결을 `reauth_required`로 둔다.

성공 결과: 반복 로그인으로 카드사 계정이 잠기지 않는다.

### O03. 카드사 추가 인증

1. 카드사가 앱 승인 또는 OTP를 요청한다.
2. TimeFit이 제한시간과 인증 방법을 표시한다.
3. 사용자가 카드사 앱 승인 또는 OTP 입력을 완료한다.
4. 기존 session에서 인증을 계속한다.
5. 성공 후 OTP와 challenge를 즉시 폐기한다.

실패:

- 만료 시 새로운 challenge 생성
- 반복 실패 시 자동 시도 중단
- CAPTCHA는 우회하지 않고 지원 범위를 안내

### O04. 자동 동기화 재인증

1. 기존 연결의 카드사 session 또는 인증정보가 만료된다.
2. TimeFit이 자동 재시도를 중단한다.
3. 소유자에게 `카드사 재인증 필요` 알림을 보낸다.
4. 소유자가 연결 관리에서 재인증한다.
5. 인증 성공 후 실패 지점부터 수집한다.

성공 결과: 재인증 중에도 기존 카드·거래·결산은 유지된다.

### O05. 카드사 연결 일시정지

1. 소유자가 연결 관리에서 `일시정지`를 선택한다.
2. 적용 시점과 영향을 확인한다.
3. TimeFit이 신규 job 생성을 중단한다.
4. 기존 원장은 유지한다.
5. 재개 시 마지막 cursor부터 증분 수집한다.

### O06. 카드사 연결 해제

1. 소유자가 연결 해제를 누른다.
2. 신규 동기화 중단, 인증정보 폐기와 기존 원장 보존을 안내한다.
3. 소유자가 해제를 확정한다.
4. queued/running job을 취소한다.
5. Connector session을 종료한다.
6. Vault credential을 폐기한다.
7. 연결 상태를 `disconnected`로 변경한다.

성공 결과:

- 해제 후 카드사 신규 호출 0건
- 과거 지출·증빙·확정 결산 유지
- 해제자·시각·사유 감사 기록

## 5. 비용관리자 시나리오

### M01. 보유카드 선택

1. 인증 후 발견된 카드 목록을 확인한다.
2. 자동 수집할 카드를 선택한다.
3. 제외할 카드는 체크하지 않는다.
4. `선택 카드 연결`을 누른다.

성공 결과:

- 선택한 카드만 corporate card로 활성화
- 같은 카드를 재조회해도 중복 등록 없음
- 선택하지 않은 카드 거래는 원장에 반영되지 않음

### M02. 카드 담당자 지정

1. 카드별 담당 직원을 검색한다.
2. 필요하면 부서와 매장도 지정한다.
3. 적용 시작일을 설정한다.
4. 증빙 요청 사용 여부를 선택한다.
5. 저장한다.

성공 결과:

- 적용일 이후 거래에 담당자가 자동 지정된다.
- 과거 담당자는 명시적 일괄 변경 전까지 유지된다.
- 변경자와 적용기간이 기록된다.

### M03. 여러 카드 일괄 지정

1. 동일 부서에서 사용하는 카드 여러 장을 선택한다.
2. `담당자 일괄 지정`을 누른다.
3. 직원·부서·매장과 적용일을 입력한다.
4. 변경될 카드와 거래 범위를 미리 확인한다.
5. 저장한다.

성공 결과: 성공·제외·실패 카드 수를 결과로 보여주고 별도 완료 팝업 없이 화면을 갱신한다.

### M04. 최근 90일 최초 수집 확인

1. 카드 선택 후 최초 수집 화면을 확인한다.
2. 전체·카드별 진행률을 본다.
3. 화면을 닫고 다른 업무를 한다.
4. 다시 접속해 이어진 진행률을 확인한다.
5. 실패 카드만 재시도한다.

성공 결과:

- 브라우저 종료와 무관하게 작업 지속
- 카드·기간·페이지별 재개
- 신규·중복·실패 건수 표시

### M05. CSV 대사

1. 같은 기간의 카드사 CSV/XLSX를 준비한다.
2. 대사 화면에 파일을 업로드한다.
3. 카드·승인일시·금액·승인번호 열 매핑을 확인한다.
4. 수집 결과와 일별 건수·순액을 비교한다.
5. 차이 거래를 확인한다.
6. 차이가 없으면 대사를 확정한다.

성공 결과:

- 30일 이상 일별 순액 100% 일치
- 파일 hash와 대사 결과 보존
- 통과 후 연결 `active`

### M06. 대사 차이 처리

가능한 차이:

- API 누락
- CSV 중복
- 부분취소 연결 실패
- 승인·매입 금액 차이
- 해외결제 환율 차이
- 재발급 카드 식별 실패

진행:

1. 관리자가 차이 항목을 선택한다.
2. TimeFit이 원인 후보와 원본 source를 표시한다.
3. 재수집 또는 수동 연결을 선택한다.
4. 해결되지 않으면 Connector 운영 이슈로 전달한다.

### M07. 신규 카드 발견

1. 일일 카드 목록 조회에서 신규 카드가 발견된다.
2. 관리자가 신규 카드 알림을 확인한다.
3. 카드 담당자와 수집 여부를 지정한다.
4. 선택하면 해당 카드의 90일 또는 발급 이후 내역을 수집한다.

성공 결과: 관리자 확인 전 신규 카드는 자동으로 지출 원장에 반영되지 않는다.

### M08. 카드 재발급

1. 새 token의 카드가 발견된다.
2. TimeFit이 카드명·last4·카드사 관계를 이용해 재발급 후보로 표시한다.
3. 관리자가 이전 카드를 선택한다.
4. 이전 카드는 inactive, 새 카드는 active로 전환한다.
5. 담당자 정책을 새 카드에 이어받을지 선택한다.

### M09. 카드 해지

1. 카드사 조회에서 해지 상태가 확인된다.
2. 해당 카드 신규 수집을 중단한다.
3. 관리자에게 상태 변경을 표시한다.
4. 과거 거래와 증빙은 유지한다.

### M10. 예외 거래 검토

1. 관리자가 `지출관리 > 예외 검토함`을 연다.
2. 미증빙·금액차이·중복의심·취소 미연결을 확인한다.
3. 담당자 재지정, 영수증 요청, 거래 연결 또는 제외를 처리한다.
4. 일괄 처리 전 영향 건수와 금액을 확인한다.

## 6. 카드 담당 직원 시나리오

### E01. 신규 거래 증빙 제출

1. 직원이 신규 지출 알림을 받는다.
2. `내 증빙 요청`에서 거래를 연다.
3. 금액·일시·가맹점·카드 last4를 확인한다.
4. 사유·프로젝트·태그를 입력한다.
5. 영수증을 촬영하거나 업로드한다.
6. OCR 결과를 확인하고 제출한다.

성공 결과:

- 직원은 원본 카드 금액을 수정할 수 없다.
- 영수증과 카드 거래가 연결된다.
- 제출자·시각·수정 이력이 기록된다.

### E02. 영수증 중복 업로드

1. 이미 제출한 영수증을 다시 업로드한다.
2. TimeFit이 file hash와 OCR 특징을 검사한다.
3. 기존 영수증 후보를 표시한다.
4. 중복이면 새 문서를 생성하지 않는다.

### E03. 영수증 금액 불일치

1. 80,000원 카드 거래에 100,000원 영수증을 업로드한다.
2. TimeFit이 부분취소 또는 잘못된 영수증 가능성을 표시한다.
3. 자동 확정을 금지한다.
4. 직원이 설명을 추가하거나 다른 영수증을 제출한다.

### E04. 잘못 지정된 거래

1. 직원이 자신이 사용하지 않은 거래를 확인한다.
2. `내 거래가 아님`을 선택하고 사유를 입력한다.
3. 비용관리자 예외함으로 이동한다.
4. 관리자가 올바른 담당자로 재지정한다.

### E05. 관리자 보완 요청

1. 관리자가 증빙을 반려하고 보완 내용을 작성한다.
2. 직원이 요청 알림을 받는다.
3. 사유 또는 영수증을 수정한다.
4. 재제출한다.

## 7. 거래 처리 시나리오

### T01. 정상 승인·매입

```text
승인 100,000
→ 매입 100,000
→ 최종 지출 100,000 / acquired
```

### T02. 전체취소

```text
승인 100,000
→ 전체취소 100,000
→ 최종 순액 0 / cancelled
```

승인과 취소를 별도 지출로 합산하지 않는다.

### T03. 부분취소

```text
승인 100,000
→ 부분취소 20,000
→ 매입 80,000
→ 최종 순액 80,000 / partially_cancelled
```

### T04. 승인 없이 매입 발견

1. 대응 승인 없는 매입이 수집된다.
2. 임시 거래 그룹을 만든다.
3. `review_required`로 표시한다.
4. 추후 승인 수집 시 재결합한다.

### T05. 해외 결제

1. 승인 시 현지통화와 예상 KRW를 표시한다.
2. 매입 시 최종 환율·수수료·KRW를 반영한다.
3. 승인 대비 차이를 변경 이력으로 표시한다.

### T06. 결산 후 취소

1. 확정된 전월 거래의 취소가 수집된다.
2. 전월 snapshot은 수정하지 않는다.
3. 당월 조정분을 생성한다.
4. 필요하면 권한 있는 소유자가 전월을 재오픈한다.

## 8. 시스템 장애 시나리오

### F01. 카드사 점검

- 연결 상태: maintenance/degraded
- 동작: 점검 종료 후 자동 예약
- 사용자: 별도 조치 없음
- 기존 거래: 유지

### F02. 호출 제한

- 작업 상태: retry_scheduled
- 동작: Retry-After 또는 지수 backoff
- 다른 카드: 계속 처리

### F03. 일부 페이지 실패

- 완료 페이지와 cursor 보존
- 실패 페이지부터 재개
- 전체 완료 전 `succeeded_through` 최종 전진 금지

### F04. 카드사 화면·응답 변경

- 빈 결과를 정상으로 저장하지 않음
- Connector 자동 차단
- 운영자 긴급 경보
- 고객에게 `안전 확인 중` 표시
- 기존 카드·거래 삭제 금지

### F05. Worker 중단

- heartbeat 중단 감지
- lease 만료 후 다른 Worker 회수
- 마지막 cursor부터 재개
- 중복 이벤트 제외

## 9. TimeFit 운영자 시나리오

### P01. Connector 오류율 급증

1. 운영자가 카드사별 성공률 경보를 받는다.
2. 인증·점검·429·network·schema 오류를 구분한다.
3. schema 오류면 kill switch를 활성화한다.
4. fixture를 재생해 변경 지점을 찾는다.
5. 새 Connector version을 테스트한다.
6. Git main을 거쳐 배포한다.
7. 제한된 연결부터 재개한다.

### P02. 고착 작업 복구

1. 운영 콘솔에서 장기 running job을 확인한다.
2. heartbeat와 lease 상태를 확인한다.
3. 안전하게 lease를 만료하고 재예약한다.
4. 중복·cursor 이상 여부를 확인한다.

### P03. 고객지원 접근

1. 고객이 지원 접근 범위와 기간을 승인한다.
2. 운영자에게 TTL이 있는 break-glass 권한을 발급한다.
3. 민감 원문 없이 상태와 오류부터 확인한다.
4. 모든 조회·조치를 감사 로그에 남긴다.
5. TTL 종료 후 자동 회수한다.

## 10. 보안 시나리오

### S01. 다른 회사 카드 접근

1. 조직 A 관리자가 조직 B connection ID를 요청한다.
2. API가 membership·permission·객체 organization을 검사한다.
3. 403을 반환한다.
4. 조직 B 카드사·last4·존재 여부를 노출하지 않는다.

### S02. 인증 오류 중 secret 보호

1. Connector 인증 중 예외가 발생한다.
2. logger가 ID/PW·인증서·OTP·PAN 필드를 제거한다.
3. UI에는 오류코드와 해결 방법만 표시한다.

### S03. 전체 카드번호 수신

1. 카드사가 전체 PAN을 반환한다.
2. 격리 Runtime에서 조직별 HMAC token과 last4를 만든다.
3. PAN 메모리를 폐기한다.
4. 일반 API·DB·Queue에는 token과 last4만 전달한다.

## 11. 알림 시나리오

| 상황 | 대상 | 시점 | 반복 |

## 12. 인수 기준

1. 회사 소유자가 TimeFit 안에서 카드사 인증을 완료한다.
2. 보유카드를 자동 발견하고 선택한다.
3. 선택 카드에 직원·부서·매장을 지정한다.
4. 90일 최초 수집이 화면 종료 후에도 진행된다.
5. 승인·전체취소·부분취소·매입 순액이 정확하다.
6. 동일 기간 3회 수집 후 중복 합산이 없다.
7. 실패 페이지부터 재개한다.
8. 카드 재발급·해지·동일 last4를 안전하게 처리한다.
9. 인증서 만료와 추가 인증을 복구한다.
10. 카드사 점검·호출 제한·schema 변경을 구분한다.
11. CSV 30일 이상 일별 순액이 100% 일치한다.
12. 직원은 본인 거래만 제출할 수 있다.
13. 조직 A가 조직 B 금융정보에 접근하지 못한다.
14. PAN·CVC·인증정보가 DB와 로그에 없다.
15. 연결 해제 후 신규 카드사 호출이 없다.
16. 결산 후 취소가 확정본을 변경하지 않는다.
17. 운영자 접근은 고객 승인·TTL·감사 조건을 충족한다.
18. Pilot 2주간 P0/P1 결함이 없다.

## 13. 출시 사용자 시나리오

첫 출시에서 반드시 완주해야 할 대표 시나리오는 다음이다.

```text
회사 소유자
→ 공동인증서로 카드사 인증
→ 추가 인증 완료

비용관리자
→ 보유카드 1~10장 선택
→ 담당 직원 지정
→ 90일 수집 확인
→ CSV 대사 100%

카드 담당 직원
→ 신규 거래 확인
→ 사유·영수증 제출

비용관리자
→ 부분취소·미증빙 예외 처리

회사 소유자
→ 월 보고서 확인
→ 필요 시 재인증·연결 해제
```

이 대표 시나리오가 실제 Pilot 법인에서 반복 실행되어야 기능 출시로 판정한다.
