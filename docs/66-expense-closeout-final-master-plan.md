# TimeFit 지출·증빙·자동결산 최종 마스터 기획서

버전: 2.1  
작성일: 2026-09-10  
상태: 상세 검토 완료·구현 기준 확정안

## 1. 최종 제품 정의

> 직원이 영수증만 촬영하면 TimeFit이 카드내역과 매출을 대조하고, 관리자는 예외만 확인해 일간부터 연말까지 결산하는 매장 운영 자동화 서비스

### 핵심 제품 요구사항

> 사업자가 카드사 또는 금융 데이터 제공자를 실제로 연결하면 보유 법인카드가 자동 등록되고, 이후 승인·취소·매입 내역이 별도 파일 업로드 없이 주기적으로 자동 조회되어야 한다.

이는 선택 기능이 아니라 지출·증빙 제품의 출시 핵심 기능이다. 수동 카드 등록, 승인 이메일, CSV/Excel 업로드는 자동 연결 전 체험과 외부 서비스 장애 시 운영을 이어가기 위한 보조·복구 수단으로만 둔다.

TimeFit은 범용 회계프로그램을 복제하지 않는다. 근무·스케줄·휴가·급여·POS 매출이라는 기존 강점을 지출·증빙과 결합해 매장 관리자의 반복 입력과 대조 업무를 줄이는 데 집중한다.

## 2. 최종 의사결정

### 입력 자동화

- 영수증은 휴대폰 카메라 촬영을 첫 번째 입력 방식으로 제공한다.
- Google Cloud Vision이 사진을 OCR 텍스트로 변환한다.
- LLM은 OCR 텍스트를 정해진 JSON Schema로 구조화한다.
- 결정적 금액·날짜·사업자번호 검증은 코드가 수행한다.
- 초기에는 AI가 자동 확정하지 않고 관리자 검수 후 원장에 반영한다.

### 카드 연동

- 제품 출시 목표는 `카드사 자동 연결 → 보유카드 자동 등록 → 승인·취소·매입 자동 조회`다.
- 하이픈 테스트베드로 실제 카드 연결과 조회를 검증한 뒤 운영 연동을 활성화한다.
- API 계약·심사 전에는 `승인 이메일 자동수집 + 카드사 CSV/Excel 대조`로 개발과 시범 운영을 진행한다.
- CSV와 이메일은 운영 연동 후에도 장애·재인증 기간의 폴백으로 유지한다.
- 카드 연동 방식과 상관없이 동일한 내부 카드 거래 모델을 사용한다.

### 중복 방지

- 카드내역과 영수증은 각각 지출이 아니다.
- 하나의 `expense`에 카드 승인, 영수증, 이메일, CSV, 매입/청구 데이터가 원천자료로 연결된다.
- 결산은 원천자료가 아니라 확정된 지출 원장을 한 번만 합산한다.

### 결산

- 일간·주간·월간·연말 결산은 같은 매출·지출·급여 원장을 사용한다.
- 미마감 결산은 원장 변경 시 자동 재계산한다.
- 마감 결산은 잠금·스냅샷·버전을 유지한다.
- 마감 후 변경은 재오픈 또는 다음 기간 조정으로 처리한다.

## 4. 핵심 사용자 흐름

### 직원 영수증 제출

1. `영수증 촬영`을 누른다.
2. 안내 프레임에 맞춰 사진을 찍는다.
3. 지출 목적을 선택하거나 짧은 메모를 남긴다.
4. 제출한다.

직원에게 상호·금액·부가세·계정과목을 처음부터 입력시키지 않는다. OCR/AI 결과에 문제가 있을 때만 수정 요청을 보낸다.

### 자동 처리

```text
사진 업로드
→ 비공개 Storage
→ 이미지 품질 검사·회전·HEIC 변환
→ Google Vision OCR
→ LLM JSON 구조화
→ 금액/날짜/사업자번호 검증
→ 카드 거래 후보 탐색
→ 높은 신뢰도: 검토 가능
→ 낮은 신뢰도: 확인 필요
```

### 관리자 검수

- 원본 사진, OCR 원문, AI 필드를 나란히 확인한다.
- 시스템이 카드 매칭 후보와 판단 근거를 보여준다.
- 관리자는 `확정`, `수정 후 확정`, `기존 지출에 병합`, `제외` 중 하나만 선택한다.
- 정상 거래 전체가 아니라 예외 업무함만 처리한다.

## 5. 법인카드 최종 전략

### 보조 경로: 무료 운영 및 장애 폴백

#### 승인 이메일 자동수집

- 사업장별 전용 수신 주소 발급
- 카드사 승인 이메일 자동 전달
- 발신 도메인·DKIM/SPF 결과 확인
- 카드사별 파서로 카드, 금액, 가맹점, 승인시각, 승인번호 추출
- 원문 이메일의 개인정보를 최소 보존
- 파싱 실패 건은 관리자 예외함에 표시

이메일 데이터는 빠른 매칭 후보로 사용하고 회계 확정 데이터로 단독 신뢰하지 않는다.

#### CSV/Excel 월말 대조

- 카드사 파일 업로드
- 카드사별 컬럼 자동 매핑
- 업로드 미리보기와 오류 행 표시
- 승인·취소·매입 상태 정규화
- 이메일에서 수집한 거래와 병합
- 누락·금액 차이·중복 후보만 관리자에게 표시

### 1단계: 하이픈 실제 연결 검증

- 법인카드 조회 단품 테스트베드
- 보유카드·승인·매입 API 우선 검증
- 최근 90일 백필
- 동일 기간 CSV와 일별 합계 비교
- 카드사 장애·인증 만료·취소·지연매입 시험
- 2주간 병행 후 오합산 0건 확인

### 2단계: 하이픈 운영 자동조회

- OAuth 토큰은 서버에서만 발급·저장
- 최초 90일 백필
- 6시간 주기 증분 동기화
- 야간 최근 7일 재조회
- 월초 전월 매입·청구 대조
- 사용량이 많은 사업장만 1~3시간 주기로 조정

비용 기준은 법인카드 단품 TR슬림 월 10만원 + 건당 과금 또는 TR시그니처 월 30만원부터다. 실제 건당 단가와 포함량은 계약 전 견적을 받아 결정한다.

## 6. 중복 방지 설계

```text
승인 이메일 ─┐
카드 CSV     ├─ expense_sources ─ expense 1건 ─ 결산 1회 합산
하이픈 API   ┤
영수증 사진 ─┘
```

### 식별 우선순위

1. 제공자 고유 거래 ID
2. 카드 식별자 + 승인번호 + 승인일시 + 금액 + 승인/취소
3. 카드 + 정규화 가맹점 + 일시 + 금액
4. 영수증의 사업자번호 + 일시 + 금액 + 승인번호
5. 원본 파일 SHA-256

### 병합 정책

- 승인→매입→청구는 새 지출이 아니라 같은 카드 거래의 상태 변경이다.
- 승인 취소는 원승인과 연결된 반대 거래로 보존한다.
- 영수증이 먼저 들어오면 임시 지출을 생성하고 카드내역 도착 시 병합한다.
- 카드내역이 먼저 들어오면 미증빙 후보를 만들고 영수증 도착 시 연결한다.
- 불확실한 유사 거래는 자동 병합하지 않고 비교 화면을 제공한다.
- 병합과 해제는 모두 감사 로그에 기록한다.

## 7. 결산 설계

### 일간

- POS 총매출·순매출·취소
- 카드/현금/기타 결제수단별 매출
- 확정 지출과 증빙 완료율
- 실제/예상 인건비
- 영업 공헌이익
- 카드 미증빙과 매출 정산 차이

### 주간

- 일별 매출·지출·인건비 추이
- 전주 대비 증감
- 주요 거래처·계정과목
- 미증빙·미매칭 누적
- 스케줄 인건비 대비 실제 인건비

### 월간

- 순매출, 지출, 인건비, 영업이익
- 공급가액·부가세
- 카드별 이용·취소·결제예정
- 증빙 완결성
- 전월/전년 동월 비교
- 세무사 전달과 Excel 내보내기
- 마감 잠금과 재오픈

### 연말

- 월별 손익 및 전년 대비
- 계정과목·거래처·카드별 합계
- 급여·인건비 합계
- 미증빙·조정·재오픈 이력
- 세무 원장과 증빙 인덱스

## 8. 관리자 리소스 최소화

- 정상 건은 자동 분류·추천·결산 초안 생성
- 업무함에는 저신뢰 OCR, 미증빙, 미매칭, 중복 의심, 동기화 실패, 정산 차이만 표시
- 같은 가맹점의 계정과목·사유 재사용
- 카드별 기본 사용자와 계정과목
- 반복 결제 자동 식별
- 신뢰도 높은 추천 일괄 승인
- 건별 알림 대신 일간 요약과 마감 임박 요약
- 오류 메시지마다 원인, 영향 범위, 해결 버튼 제공

핵심 KPI는 관리자 1건당 처리시간, 자동 처리율, 월마감 소요시간, 오매칭 해제율, 결산 재오픈 횟수다.

## 9. 데이터 모델

### 핵심 원장

- `expenses`: 확정 지출
- `sales_orders`: POS 매출 원천
- `payroll_drafts/lines`: 확정 인건비
- `closeouts`: 기간별 결산 스냅샷과 버전

### 증빙·AI

- `expense_documents`: 원본 사진/PDF
- `expense_processing_runs`: OCR/LLM 처리 시도와 버전
- `expense_sources`: 영수증·이메일·CSV·API와 지출 연결

### 카드

- `corporate_cards`: 카드사, 별칭, 마스킹 번호, 담당자, 연결 상태
- `card_connections`: provider, 인증 참조값, 상태, 만료, 마지막 동기화
- `card_sync_runs`: 기간, 상태, 호출수, 비용, 오류
- `card_transactions`: 승인·취소·매입·청구의 정규화 데이터
- `expense_matches`: 카드 거래와 지출의 N:M 연결

### 운영

- `business_contacts`: 거래처
- `expense_categories`: 계정과목
- `expense_tags`: 1·2차 관리 태그
- `expense_audit_logs`: 모든 변경의 before/after

모든 테이블은 `organization_id` 기준 RLS를 사용한다. 외부 서비스 비밀값과 카드사 인증정보는 클라이언트 또는 일반 컬럼에 평문으로 저장하지 않는다.

## 11. 구현 단계

### Phase 1 — 카드 원장 기반과 폴백

- 지출·증빙 정보구조
- 카드 등록·상태·담당자
- CSV 승인내역과 중복 차단
- 이메일 수신 주소와 카드사 파서
- 원천자료·지출 단일 원장·감사 로그
- 거래처와 계정과목 기본 구조

### Phase 2 — 법인카드 자동 연결

- 하이픈 Provider Adapter
- 소유자 인증·동의·카드사 연결
- 보유카드 자동 조회·선택·등록
- 최근 90일 승인·취소·매입 백필
- 주기적 자동조회·재시도·재인증
- CSV 병행 대조와 오합산 검증

### Phase 3 — 촬영·OCR·AI

- 모바일 영수증 촬영
- 이미지 품질 검사
- Google Vision OCR
- LLM JSON 구조화
- 원본/텍스트/필드 비교 검수
- 카드·영수증 자동 매칭 후보

### Phase 4 — 매출과 자동결산

- Toss Place 매출 연결
- 일간·주간·월간 결산
- 실제 인건비 반영
- 예외 업무함
- 마감 잠금·버전·재오픈

### Phase 5 — 연말과 카드 고도화

- 청구·결제예정·한도
- 연말 결산
- 세무사 공유

### Phase 6 — 고도화

- 조건부 자동 확정
- 복수 POS/배달채널
- 계좌·현금영수증·세금계산서 연동

- 자산·부채·현금흐름 예측

## 12. 출시 게이트

1. 카드내역과 영수증이 결산에 한 번만 반영된다.
2. 이메일·CSV·API 재수집이 중복 거래를 만들지 않는다.
3. 승인·취소·부분취소·매입 지연을 복구할 수 있다.
4. 원본→OCR→AI→수정→원장→결산을 추적할 수 있다.
5. 마감 숫자가 원장 변경으로 조용히 바뀌지 않는다.
6. 조직 간 데이터·파일 격리 테스트를 통과한다.
7. 외부 서비스 장애에도 기존 데이터가 유지된다.
8. 관리자가 예외 업무함만 처리해 월마감할 수 있다.
9. 하이픈 도입 전 CSV와 API의 일별 합계가 2주 연속 일치한다.
10. 자동 확정은 오합산 0건과 목표 정확도 달성 후에만 활성화한다.

## 13. 성공 기준

- 영수증 제출 30초 이내
- 일반 영수증 처리 결과 1분 이내
- 관리자 거래당 검수 20초 이하
- 카드·증빙 자동 후보 매칭률 90% 이상
- 확인된 오매칭률 0.5% 미만
- 중복 결산 반영 0건
- 월마감 관리자 작업시간 70% 이상 절감
- 일간 손익을 다음 영업일 오전 전에 제공

## 15. 최종 상세 검토 결론

기존 설계의 제품 방향과 단일 지출 원장 원칙은 유지한다. 다만 운영 가능한 법인카드 연결을 위해 다음 항목을 구현 필수 조건으로 승격한다.

1. `수동 카드 등록`과 `금융사 연결`을 서로 다른 기능과 상태로 표시한다.
2. 연결 한 번으로 끝난다고 표현하지 않고 인증 만료·카드사 점검·부분 실패를 정상 운영 상태로 취급한다.
3. 승인, 취소, 매입, 청구 데이터를 각각 지출로 생성하지 않고 하나의 카드 거래 생명주기로 관리한다.
4. API, 이메일, CSV가 동시에 들어와도 하나의 거래로 수렴해야 한다.
5. 카드 연결이 끊겨도 이미 수집된 지출과 결산은 유지되고 CSV로 계속 운영할 수 있어야 한다.
6. 영수증이 없는 카드 거래와 카드 거래가 없는 영수증을 각각 예외 업무함에서 추적한다.
7. 자동 분류와 자동 매칭은 가능하지만 자동 결산 확정은 품질 기준을 통과한 조직에만 단계적으로 연다.

현재 구현은 카드 메타데이터 등록과 CSV 가져오기까지다. 화면의 `법인카드 등록`은 실제 카드사 연결로 오인될 수 있으므로 다음 릴리스에서 `카드 수동 등록`으로 명칭을 바꾸고 별도의 `카드사 연결` 진입점을 제공해야 한다.

## 16. 법인카드 연결 상세 UX

### 연결 전 선택

`법인카드 추가`를 누르면 다음 두 방식을 먼저 선택한다.

| 방식 | 화면 명칭 | 용도 | 비용 | 데이터 신선도 |
|---|---|---|---:|---|
| 금융 API | 카드사 자동 연결 | 승인·취소·매입 자동 수집 | 유료 전환 가능 | 최근 동기화 기준 |
| 파일 | 카드 수동 등록·내역 가져오기 | 무료 MVP·API 장애 대체 | API 비용 없음 | 업로드 시점 |

승인 이메일 수집은 관리자가 별도 카드를 만드는 방식이 아니라, 수동 카드에 연결할 수 있는 `빠른 승인 알림` 옵션으로 제공한다.

### 자동 연결 마법사

```text
1. 안내·동의
→ 2. 사업자 유형 선택
→ 3. 인증 방식 선택
→ 4. 카드사 인증
→ 5. 조회된 카드 선택
→ 6. 카드별 사용자·별칭 지정
→ 7. 최근 90일 가져오기
→ 8. 합계 검증
→ 9. 연결 완료
```

#### 1. 안내·동의

- 수집 항목, 목적, 보관기간, 제3자 제공 여부를 표시한다.
- 카드번호 전체와 CVC를 TimeFit이 저장하지 않는다고 명시한다.
- 스크래핑 연동은 즉시 승인 알림이 아니라 주기 조회라는 점을 알린다.
- 기존 CSV 거래가 있으면 자동으로 중복 대조된다고 안내한다.

#### 2~4. 사업자와 인증

- 법인사업자와 개인사업자의 지원 카드사·인증 방식 차이를 분기한다.
- 공동인증서, 카드사 ID/PW 등 실제 방식은 하이픈 계약 명세를 기준으로 동적 표시한다.
- 인증정보 입력 화면은 TimeFit 일반 프런트엔드 로그·분석 도구에 노출하지 않는다.
- 가능한 경우 하이픈이 발급하는 참조값만 보관한다. TimeFit이 복호화 가능한 비밀번호나 인증서 비밀번호를 장기 저장해야 한다면 운영 도입을 중단한다.

#### 5~6. 카드 선택과 담당자

- 조회된 카드의 카드사, 카드명, 끝 4자리, 상태만 표시한다.
- 동일한 끝 4자리가 존재하므로 provider 카드 ID를 내부 고유키로 사용한다.
- 카드마다 주 사용자, 부서, 기본 계정과목, 영수증 제출 책임자를 지정할 수 있다.
- 공용 카드는 담당자를 복수 지정하고 거래별 사용자를 선택할 수 있다.

#### 7~9. 최초 동기화

- 최근 90일을 7~14일 단위로 나눠 가져오며 진행률을 표시한다.
- 기존 이메일·CSV 거래와 병합한 결과를 `신규/병합/검토 필요/실패`로 나눈다.
- API와 CSV의 일별 승인·취소 순액이 다르면 연결 완료가 아니라 `대조 필요`로 종료한다.
- 연결 직후 자동결산 반영은 하지 않고 검증 완료 후 원천 우선순위를 API로 승격한다.

### 연결 후 카드 화면

카드별로 다음 정보를 한 화면에서 보여준다.

- `연결 정상`, `동기화 중`, `일부 실패`, `재인증 필요`, `점검 중`, `연결 해제` 상태
- 마지막 성공 시각, 마지막 시도 시각, 다음 예정 시각
- 최근 동기화에서 신규·갱신·취소·실패한 건수
- 승인액, 취소액, 순이용액, 미매입액, 결제예정액
- 미증빙 거래 수, 영수증 자동 매칭률, 담당자 미지정 건수
- `지금 동기화`, `재인증`, `CSV 가져오기`, `연결 설정`, `연결 해제`

`연결 해제`는 과거 거래를 삭제하지 않는다. 자동 동기화와 인증 참조만 중지·파기하고 보존 의무가 있는 원장과 감사 기록은 유지한다.

## 17. 카드 거래 생명주기와 정합성

### 상태 모델

```text
승인 대기 없이 수집
  ├─ 승인 → 매입 → 청구 → 결제
  ├─ 승인 → 전체 취소
  ├─ 승인 → 부분 취소 → 잔액 매입
  └─ 승인 → 미매입 장기화 → 확인 필요
```

내부 `card_transaction_group`이 한 결제의 정체성을 나타내며, 공급자가 제공한 각 승인·취소·매입·청구 레코드는 변경 불가능한 `card_transaction_events`로 보존한다. 화면과 결산에서 사용하는 현재 상태는 이벤트를 합성해 만든다.

### 금액 규칙

- 승인액은 빠른 운영 확인용이다.
- 매입액은 월 결산의 기본 카드 지출 금액이다.
- 매입 전 기간에는 승인액을 `잠정 지출`로 보여주되 확정액과 구분한다.
- 취소는 원거래 삭제가 아니라 음수 효과를 가진 연결 이벤트다.
- 부분취소 후 순액만 결산에 반영한다.
- 해외 이용은 원화 청구액이 도착하기 전 원통화 승인액을 잠정 표시한다.
- 팁·환율·수수료 등 승인과 매입 차이는 같은 거래의 조정으로 기록한다.

### 원천 우선순위

| 필드 | 1순위 | 2순위 | 3순위 |
|---|---|---|---|
| 거래 상태·매입액 | API 매입/청구 | 카드사 CSV | 승인 이메일 |
| 승인시각·승인번호 | API 승인 | 카드사 CSV | 영수증/OCR |
| 가맹점 사업자번호 | 영수증·세금증빙 | API/CSV | 거래처 규칙 |
| 계정과목·사유 | 관리자 확정 | 조직 자동화 규칙 | AI 추천 |
| 증빙 원본 | 영수증 사진/PDF | 세금계산서 연결 | 없음 |

관리자가 확정한 값은 새 동기화가 조용히 덮어쓰지 않는다. 외부 원천의 변경은 차이로 표시하고 재확정을 요청한다.

### 멱등성과 중복 방지

- 공급자 이벤트는 `(organization_id, provider, provider_event_id)`로 유일해야 한다.
- 대체 키는 카드 provider ID, 승인번호, 승인시각, 금액, 거래 유형을 결합한다.
- 파일은 SHA-256, 행은 파일 ID와 원본 행 번호, 이메일은 Message-ID로 재처리를 차단한다.
- 영수증 후보는 승인번호 일치에 가장 높은 점수를 주고, 금액·시간·카드 끝자리·가맹점·사업자번호로 보정한다.
- 고신뢰 후보도 초기에는 관리자가 확정하며, 서로 비슷한 후보가 두 개 이상이면 자동 병합하지 않는다.
- 지출에는 조직별 불변 `ledger_entry_id`를 부여하고 결산은 이 키를 한 번만 합산한다.

## 18. 카드 연결 서버·데이터 설계

### 서비스 경계

```text
웹/모바일
→ TimeFit Card API
→ 연결·동의 서비스
→ Provider Adapter(Hyphen/CSV/Email)
→ 원문 격리 저장소
→ 정규화·중복 판정
→ 영수증 매칭
→ 지출 원장
→ 결산 스냅샷
```

프런트엔드는 하이픈 HKey나 액세스 토큰을 직접 사용하지 않는다. 공급자 응답 구조 또한 UI에 직접 노출하지 않고 어댑터에서 공통 모델로 변환한다.

### 필수 테이블 보강

- `card_connections`: 공급자, 사업자 유형, 상태, 동의 버전, credential reference, 만료시각
- `connection_assets`: 연결에서 발견한 카드와 TimeFit 카드의 매핑
- `card_sync_cursors`: 카드·데이터 종류별 마지막 성공 범위
- `card_sync_runs`: 요청 범위, 결과 건수, 재시도, 비용 추정, 오류 분류
- `card_transaction_events`: 원천별 변경 불가능한 승인·취소·매입·청구 이벤트
- `card_transaction_groups`: 합성된 현재 거래 상태와 순액
- `expense_matches`: 거래 그룹과 영수증/지출의 후보 점수·근거·확정자
- `connection_consents`: 동의문 버전, 동의자, 시각, 철회 시각

### 연결 상태

`draft → authenticating → backfilling → reconciling → active`를 정상 흐름으로 사용한다. 오류는 `degraded`, 사용자의 조치가 필요하면 `reauth_required`, 중지 시 `paused`, 해제 시 `disconnected`로 둔다.

동기화 실행은 `queued → running → succeeded/partial/failed`로 관리한다. 동일 조직·연결·조회범위의 작업이 동시에 실행되지 않도록 잠금과 멱등 키를 둔다.

### 동기화 정책

- 기본: 6시간 간격
- 사용자가 지출 사유를 바로 작성해야 하는 활성 카드: 영업시간 중 1시간 간격
- 매일 야간: 최근 7일 승인·매입 재조회
- 매월 1~3일: 전월 전체 매입·청구 대조
- 수동 새로고침: 5분 쿨다운과 비용 안내
- 실패: 지수 백오프 후 부분 범위 재시도
- 장기 실패: CSV 대체 경로를 즉시 제공

실제 그랜터도 기본 일 3회, 담당자가 연결된 카드·계좌는 영업시간대 약 1시간 주기를 안내한다. TimeFit은 `실시간`이라는 모호한 표현 대신 마지막 성공 시각과 예상 갱신주기를 표시한다.

## 19. 보안·개인정보·운영 통제

- 카드번호 전체, CVC, 카드 비밀번호를 저장하지 않는다.
- 카드번호가 원문 응답에 포함되면 정규화 전에 토큰화·마스킹하고 제한 저장소에 격리한다.
- HYPHEN User ID/HKey와 OAuth 토큰은 서버 비밀 또는 암호화 저장소에서만 다룬다.
- 조직별 인증 참조값은 애플리케이션 데이터와 분리하고 키 회전·접근 기록을 남긴다.
- 로그, 오류 추적, 분석 도구에서 인증정보와 금융 원문을 필터링한다.
- 연결·재인증·해제, 담당자 변경, 지출 병합·해제, 결산 재오픈을 감사 로그에 기록한다.
- RLS뿐 아니라 서버 함수에서 소유자 권한과 `organization_id`를 다시 검증한다.
- 다운로드 파일에는 워터마크·내보낸 사람·시각을 기록하고 만료 링크를 사용한다.
- 보존기간 종료와 조직 탈퇴 시 원본, 인증 참조, 파생 데이터의 파기 절차를 분리 정의한다.

하이픈이 전달자 역할만 하고 데이터 내용을 보관·관리하지 않는다고 안내하므로, TimeFit이 저장하는 원문과 파생 데이터에 대한 보안·보존 책임은 TimeFit 설계에서 별도로 해결해야 한다.

## 20. 그랜터 비교와 TimeFit 차별화

### 반드시 따라잡을 기준

- 공동인증서 또는 개별 로그인 기반 금융자산 연결
- 카드별 담당자 지정
- 카드 거래 자동 수집과 상세 조회
- 계정과목·사유·태그 자동화 규칙
- 미작성 사유 업무함과 담당자 알림
- 거래와 첨부파일·세금계산서 연결
- 카드·계좌·매출을 포함한 기간 분석

### TimeFit이 더 강해야 하는 부분

- 별도 메신저 없이 TimeFit 직원 앱에서 촬영·사유 제출을 끝낸다.
- 카드 사용자와 실제 근무자·근무시간·매장을 이미 알고 있어 비용 책임자를 더 정확히 추천한다.
- POS 매출, 실제 인건비, 스케줄 인건비, 지출을 같은 일간 손익에 연결한다.
- 카드가 없는 현장 영수증도 OCR로 같은 원장에 들어온다.
- 거래 수집 실패 시 이메일·CSV로 자연스럽게 강등되어 결산이 멈추지 않는다.
- 중복의 근거와 병합 이력을 관리자가 확인·해제할 수 있다.
- 범용 회계 기능보다 매장별 일간마감과 예외 최소화에 집중한다.

## 21. 구현 우선순위와 수용 테스트

### Release A — 연결 기반과 안전한 폴백

- 현재 `법인카드 등록`을 `카드 수동 등록`으로 변경
- CSV 컬럼 매핑·미리보기·오류 행 다운로드
- 승인/취소/부분취소와 원거래 연결
- 카드 담당자·기본 계정과목·영수증 책임자
- 카드 연결·이벤트·지출 원장 기반
- 중복 의심·동기화 실패 예외 업무함

### Release B — 하이픈 자동 연결

- Provider Adapter와 연결 상태 모델
- 서버 OAuth 토큰 캐시·갱신
- 보유카드 조회와 카드 선택
- 최근 90일 백필 및 진행률
- 승인·매입·취소 정규화
- CSV 병행 대조 리포트
- 연결 완료 후 예약 자동조회

### Release C — 영수증 촬영·OCR·자동 매칭

- 모바일 영수증 촬영·갤러리 업로드
- Google Vision OCR와 LLM JSON 구조화
- 원본·OCR·추출 필드 검수
- 카드·영수증 매칭과 병합·해제
- 미증빙·미매칭·저신뢰 OCR 예외 업무함

### Release D — 제한 운영과 제품 출시

- 내부 사업장 한 곳, 핵심 카드 한 장으로 2주 병행
- 실패 재시도·재인증·카드사 점검 UX
- 사용량·호출비용·데이터 신선도 모니터링
- 오합산 0건 확인 후 3~5개 사업장으로 확대

### 필수 수용 테스트

1. 같은 CSV를 세 번 올려도 거래와 결산은 한 번만 증가한다.
2. 같은 거래가 이메일, CSV, API 순서로 도착해도 한 지출로 수렴한다.
3. 승인 후 전체취소와 부분취소의 순액이 정확하다.
4. 승인월과 매입월이 달라도 설정된 결산 기준에 맞게 귀속된다.
5. 해외 승인 후 원화 청구액 변경을 조정 이력으로 남긴다.
6. 영수증을 먼저 올리거나 카드 거래가 먼저 와도 동일하게 매칭된다.
7. 유사 거래가 두 건이면 자동 병합하지 않는다.
8. 관리자가 수정한 계정과목을 API 재수집이 덮어쓰지 않는다.
9. 연결이 끊겨도 과거 지출과 마감 결산은 유지된다.
10. 재인증 후 누락 기간만 복구하고 중복을 만들지 않는다.
11. 다른 조직의 카드·거래·영수증·원문 파일에 접근할 수 없다.
12. 연결 해제 후 예약 동기화가 중단되고 인증 참조가 파기된다.
13. 마감 후 들어온 취소는 재오픈 또는 다음 기간 조정으로만 반영된다.
14. API 장애 중 CSV로 운영한 뒤 복구해도 합계가 변하지 않는다.
15. 관리자 예외함만 처리해 월마감을 완료할 수 있다.

법인카드 자동 연결의 출시 판정은 `기능이 호출된다`가 아니라 위 테스트 통과, 2주 병행 대조의 오합산 0건, 인증정보 보안 조건 충족, 실제 견적 확정까지 모두 만족했을 때만 `Go`로 한다.

## 22. 검증 출처와 계약 전 미확정 사항

### 확인된 내용

- 하이픈 법인카드 조회는 스크래핑 방식이며 보유카드, 결제예정금액, 승인, 매입, 카드번호, 한도 조회 API를 안내한다.
- 공개 요금은 TR슬림 월 멤버십 10만원과 정상응답 건별 과금, TR시그니처 월 30만원부터다.
- 두 요금제 모두 테스트베드를 안내한다.
- 그랜터는 공동인증서 또는 개별 로그인으로 카드·계좌 등을 연결하고 카드별 담당자, 자동 분류, 사유 작성, 첨부 증빙 연결을 제공한다.
- 그랜터 안내상 기본 조회는 일 3회이며 담당자 연결 등 조건에 따라 영업시간대 약 1시간 주기를 사용한다.

### 계약 전 반드시 확인할 내용

- 카드사별 법인·개인사업자 지원 범위와 인증 방식
- 거래 고유 ID와 원승인/부분취소 연결 필드
- API별 건당 단가, 과금 단위, 기본 제공량, 부가세와 초기 비용
- 조회 가능 과거기간, 요청 기간 제한, 호출 제한
- 카드사 점검과 명세 변경 대응 SLA
- 인증정보 보관 주체와 credential reference 지원 여부
- 최종 고객에게 데이터를 제공하고 결산에 활용할 계약상 권리
